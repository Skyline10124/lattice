# Development

This guide covers how to set up a local LATTICE development environment, the
cargo commands used to build/test/lint the workspace, the enforced code style,
and the branch and pull-request conventions. For the broader workspace
architecture, see [docs/ARCHITECTURE.md](./ARCHITECTURE.md); for the `agent.toml`
profile schema and provider configuration, see [docs/CONFIGURATION.md](./CONFIGURATION.md).
For workspace-level architecture guidance aimed at contributors, read
[AGENTS.md](../AGENTS.md) and the crate-local `AGENTS.md` in the
`crates/<crate>/` directory you intend to edit.

LATTICE is a Rust Cargo workspace of 21 crates (see `Cargo.toml`). It requires
Rust **1.94+** (edition 2024) and pins rustc **1.96.0** via
`rust-toolchain.toml`. This is a Rust project — there is no
`package.json` and no `npm` scripts; all developer commands are `cargo`
commands or `cargo xtask` subcommands. The former `scripts/` shell gates were
removed in #47 — see [docs/TESTING.md](./TESTING.md) "Retired lanes".

The development, build, test, and runtime host is Linux only. Do not preserve
generic-Unix or non-Linux compatibility branches, and do not trade away a
stronger Linux primitive for a portable fallback. The Source Tool
`wasm32-unknown-unknown` target is a guest artifact format, not a supported
host.

## Local setup

1. **Fork and clone** the repository, then `cd lattice` into the workspace root.
   The root `Cargo.toml` declares 28 workspace members: 21 product/support crates
   under `crates/`, six Source Tool crates under `tools/`, and `xtask`.
2. **Install Rust 1.94+** (edition 2024). The minimum is pinned by
   `rust-version = "1.94"`; `rust-toolchain.toml` selects the build-verified
   rustc 1.96.0 and the `wasm32-unknown-unknown` guest target.
3. **Build the Linux host binary in dev mode** (debug, unoptimized):

   ```sh
   cargo build -p lattice-cli
   ```

   Source Tool guests are wasm32 artifacts built through xtask/their explicit
   targets, not host binaries.
4. **Create an agent profile.** Profiles are discovered from
   `.lattice/agents/<name>/agent.toml` (project-local) and
   `~/.lattice/agents/<name>/agent.toml` (user-global) by
   `lattice-profile` (`crates/lattice-profile/src/discovery.rs`). The
   `.lattice/` directory is gitignored, so a fresh clone has no profile —
   create the default before running the CLI:

   ```sh
   mkdir -p .lattice/agents/default
   # Write .lattice/agents/default/agent.toml — see docs/CONFIGURATION.md
   # for the full schema, or use the templates generated by
   # lattice_profile::defaults (default/dev/reader/editor).
   ```

   A worked profile example is documented in [docs/CONFIGURATION.md](./CONFIGURATION.md)
   and the schema is enforced strictly by `lattice-profile`.

5. **Set a provider environment variable.** The router
   (`crates/lattice-llm/src/router.rs`) resolves model aliases to providers and
   reads API keys from the environment at turn time. Set one of:

   ```sh
   export ANTHROPIC_API_KEY="..."      # opus / sonnet / haiku aliases
   export OPENAI_API_KEY="..."         # gpt-* aliases
   export GEMINI_API_KEY="..."         # gemini alias
   export OPENAI_COMPATIBLE_API_KEY="..."  # openai-compatible gateway
   ```

   Profiles store only env-var *names* under `[llm]` credentials; the secret
   value is resolved and injected at turn time and is never persisted in the
   profile.

After setup, sanity-check with the non-interactive CLI (the `lattice` binary is
declared in `crates/lattice-cli/Cargo.toml`):

```sh
cargo run -p lattice-cli -- models --auth      # list authenticated models
cargo run -p lattice-cli -- doctor             # run diagnostics
```

## Manual development-state rebuild

The #139-B hard cut intentionally does not import the retired Session outcome,
numeric WorkspaceHistory, or SQLite audit/evidence formats. Rebuild only a
maintainer-selected disposable development state root; never run broad glob
deletion and never guess which `$XDG_STATE_HOME` another process uses.

1. Stop every LATTICE process using the selected state root and back up anything
   needed for forensic reference.
2. Set explicit absolute roots, derive the exact project key using the same v1
   formula as `lattice_store::ProjectStoreKey`, and print every candidate path:

   ```bash
   export STATE_ROOT=/absolute/disposable/xdg-state
   export WORKSPACE=/absolute/local-workspace
   test "${STATE_ROOT#/}" != "$STATE_ROOT"
   test "${WORKSPACE#/}" != "$WORKSPACE"
   CANON_WORKSPACE=$(realpath -e -- "$WORKSPACE")
   PROJECT_KEY=$(python3 - "$CANON_WORKSPACE" <<'PY'
   import hashlib, os, struct, sys
   raw = os.fsencode(sys.argv[1])
   digest = hashlib.sha256(
       b"lattice-project-store-key-v1\0" + struct.pack(">Q", len(raw)) + raw
   ).hexdigest()
   print(digest)
   PY
   )
   LATTICE_ROOT="$STATE_ROOT/lattice"
   PROJECT_DIR="$LATTICE_ROOT/projects/$PROJECT_KEY"
   SESSION_STORE="$LATTICE_ROOT/sessions.git"
   INVOCATION_STORE="$PROJECT_DIR/invocations.git"
   HISTORY_STORE="$PROJECT_DIR/workspace-history.git"
   LEGACY_PROJECT_AUDIT="$PROJECT_DIR/cep_audit.db"
   LEGACY_WORKSPACE_AUDIT="$CANON_WORKSPACE/.lattice/cep_audit.db"
   printf '%s\n' \
     "STATE_ROOT=$STATE_ROOT" \
     "WORKSPACE=$CANON_WORKSPACE" \
     "SESSION_STORE=$SESSION_STORE" \
     "INVOCATION_STORE=$INVOCATION_STORE" \
     "HISTORY_STORE=$HISTORY_STORE" \
     "LEGACY_PROJECT_AUDIT=$LEGACY_PROJECT_AUDIT" \
     "LEGACY_WORKSPACE_AUDIT=$LEGACY_WORKSPACE_AUDIT"
   ```

3. Inspect those exact paths. The global `sessions.git` contains every project in
   this state root: leave it alone unless the maintainer explicitly declares the
   entire root disposable. Prefer a fresh `STATE_ROOT` when existing Sessions
   matter.
4. After inspection, remove only the selected project's stores and retired audit
   files:

   ```bash
   rm -rf -- "$INVOCATION_STORE" "$HISTORY_STORE"
   rm -f -- "$LEGACY_PROJECT_AUDIT" "$LEGACY_WORKSPACE_AUDIT"
   ```

   There is no `lattice ... migrate` command, compatibility reader, automatic
   deletion, or SQLite-to-Git import.
5. Build and probe the exact state location, then create a new Session and run a
   no-Tool Turn before any Tool-bearing smoke:

   ```bash
   cargo build -p lattice-store --bin lattice-store-probe -p lattice-cli
   XDG_STATE_HOME="$STATE_ROOT" target/debug/lattice-store-probe "$LATTICE_ROOT"
   XDG_STATE_HOME="$STATE_ROOT" target/debug/lattice session new \
     --agent default --project-branch main
   # Use the printed SessionId with a profile whose enabled Tool list is empty:
   XDG_STATE_HOME="$STATE_ROOT" target/debug/lattice session send \
     <session_id> "Reply with exactly: ready"
   ```

Strict open rejects incompatible stores; that failure is a signal to inspect or
select a fresh development state root, not to add a migration fallback.

## Build commands

The CI workflow (`.github/workflows/ci.yml`) and the local mirror
`cargo xtask ci` cover the same ordinary gate on every push to `main` and on
every pull request (fmt, clippy, build `lattice`, `cargo test --workspace`,
harness/lancet boundary checks). Reproduce CI locally with `cargo xtask ci`.

| Command | Purpose |
| --- | --- |
| `cargo build -p lattice-cli` | Dev build of the shipped Linux host binary. |
| `cargo build --release -p lattice-cli` | Optimized host build; produces `target/release/lattice`. |
| `cargo build -p <guest> --target wasm32-unknown-unknown` | Build one Source Tool guest for its supported artifact target. |
| `cargo test -p <crate>` | Run tests for a single crate, e.g. `cargo test -p lattice-session`. |
| `cargo test --workspace` | Run tests across all workspace members (what CI runs). |
| `cargo clippy --workspace --all-targets -- -D warnings` | Lint all crates and targets; warnings are hard errors. |
| `cargo fmt --all -- --check` | Verify rustfmt formatting across the workspace (enforced by CI). |
| `cargo run -p lattice-cli -- <subcommand>` | Run the `lattice` binary without installing (e.g. `models --auth`, `doctor`, `session new ...`). |
| `cargo install --path crates/lattice-cli` | Install the release binary to `$CARGO_HOME/bin`. |
| `cargo xtask ci` | Local mirror of the CI lane (fmt, clippy, build `lattice`, harness boundary, `cargo test --workspace`). |
| `cargo xtask rollout --channel alpha` | Alpha rollout gate: rejects a tracked-dirty worktree, builds a locked release binary, runs Direct-Local/offline/dogfood/release-operator-matrix/doctor evidence steps against it, and writes a versioned JSON record to `target/rollout/`. See [docs/TESTING.md](./TESTING.md). |

Note: `.cargo/config.toml` defines only the `xtask` cargo alias
(`xtask = "run --package xtask --"`); it pins no `target-dir` or `TMPDIR`.
Build artifacts land in the workspace `target/` directory by cargo default.

## Code style

- **rustfmt + clippy are enforced.** CI fails on `cargo fmt --all --check` or
  any clippy warning. Run both before pushing:

  ```sh
  cargo fmt --all --check
  cargo clippy --workspace --all-targets -- -D warnings
  ```

- **No custom rustfmt/clippy config files** are present in the repo (no
  `rustfmt.toml`, `.clippy.toml`, or `clippy.toml` under the workspace root or
  `crates/`). The workspace relies on rustfmt defaults and
  `clippy -- -D warnings`. If you need to reformat, run `cargo fmt --all`
  (write) before the `--check`.

- **Copyright/SPDX header rule** (from [AGENTS.md](../AGENTS.md) "Repository
  Hygiene"): new Rust source files under `crates/**` must start with the
  workspace copyright and SPDX header:

  ```rust
  // Copyright 2026 Ast Rin
  // SPDX-License-Identifier: Apache-2.0
  ```

  Preserve existing headers when editing source files. Do not add or alter
  headers for generated, vendored, or external files unless the surrounding
  maintained source already uses that convention.

- **Do not modify `.gitignore`** in agent-driven changes (do not add ignore
  exceptions or whitelist rules to force ignored private/planning/build paths
  into commits). If a path appears to need tracking despite ignore rules, stop
  and ask a human maintainer to change the policy explicitly.

## Branch conventions

  to `main` and on all pull requests.

  `git log --oneline`). Use these prefixes:

  | Prefix | Use |

## PR process

- **Read the relevant crate `AGENTS.md` before editing.** The root
  [AGENTS.md](../AGENTS.md) gives the layered dependency graph and ownership
  rules (protocol changes start in `lancet-protocol`, CEP method changes start
  in `lancet-catalog`, provider details stay in `lattice-llm`, etc.). The
  crate-local `crates/<crate>/AGENTS.md` gives the focused key files and
  boundaries for that crate. Keep dependencies pointing from higher layers to
  lower layers; do not introduce reverse dependencies.
- **Run the full local gate before submitting** — these three are the
  CI-enforced checks:

  ```sh
  cargo test --workspace
  cargo clippy --workspace --all-targets -- -D warnings
  cargo fmt --all --check
  ```

  `cargo xtask ci` runs all three; `cargo xtask rollout --channel alpha` is the
  stronger release-evidence gate when preparing a release.
- **Record landed fixes in `FIX.md`** (append-only changelog). Per the root
  AGENTS.md "Review Records", add an entry only *after* the fix has landed,
  including issue id/severity, problem, fix summary, verification
  commands/results, and changed files when practical. Never delete or
  overwrite old `FIX.md` entries.
- **Track open/residual issues in `FINDINGS.md`** (open, deferred, partial, or
  residual issues). When fixing a finding, record the applied fix in `FIX.md`
  and remove it from the open section of `FINDINGS.md` (or move it to an
  obsolete/closed section). For partial fixes, record completed work in
  `FIX.md` and keep the remaining risk in `FINDINGS.md` with an explicit
  residual status and plan. Non-blocking notes go in `INFO.md`.
- **No PR template is enforced yet.** When the `CONTRIBUTING.md` referenced by

### Ownership quick-reference (from AGENTS.md)

- Protocol shape changes → start in `lancet-protocol`, then update catalog,
  authority, native handlers, API mapping, and tests.
- CEP method changes → start in `lancet-catalog`, then update native handlers
  and catalog-derived tool projection.
- Provider protocol details → stay in `lattice-llm`.
- Native filesystem/shell/web/mutation/verify/transport → stay in
  `lancet-native`.
- CEP runtime composition → spawn through
  `lancet_api::LancetServer`/`LancetRuntime`; do not hand-roll the
  registry/transport/server dance.
- Public session/turn API contracts → stay in `lattice-api`; TUI terminal
  lifecycle/rendering → `lattice-tui`; CLI output/argument parsing →
  `lattice-cli`.
