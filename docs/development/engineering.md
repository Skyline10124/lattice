# 工程规范

本文规定设计、代码、测试与验证的做法。目标是：每个概念归属清楚，代码让人读得懂，正确性尽量由代码结构保证，测试锁定结构保证不了的核心逻辑。

## 设计

### 归属

每个概念回答三个问题，每个问题只有一个答案：

| 问题 | 答案 |
| --- | --- |
| 状态归谁持有 | 一个组件，或一张表 |
| 规则在哪里执行 | 一个函数，或一个模块 |
| 谁只使用结果 | 其余组件：显示、转发，或据此行动 |

```text
需要为已有概念新增一条路径或一处状态:
    if 现有持有者能完成:
        交给现有持有者
    else:
        说明情况，交维护者决定归属
```

- 迁移归属时，状态、修改入口与校验一起迁移。
- 组件自己维护内部的顺序、状态与收尾；调用方发起操作并使用结果。

### 范围

- 解决当前的问题。扩展点、配置项与兼容层在出现第二个真实用途时再加。
- 方向检验：设计需要一串否定条件才能成立时，先回头检查方向。

## 代码

### 语言

新增和修改的注释、错误信息与断言消息使用中文。代码标识符、协议字段、外部 API 名称与原始错误文本保持原文。

### 可读性

| 原则 | 做法 |
| --- | --- |
| 控制流直白 | 代码按执行顺序读下来就能理解；分支用 `if` 与 `match` 显式写出 |
| 抽象克制 | trait、泛型或包装层在有两个以上真实用途时引入 |
| 冷热路径分离 | 主路径短而连续；错误处理、恢复与诊断放进独立的函数或分支 |
| 结构保证结果 | 输入在边界解析成类型，之后只传类型；用 `enum`、newtype 与 typestate 让非法状态无法构造 |
| 链式调用有分寸 | 无分支、无副作用的短变换用迭代器链；带分支、副作用或较长的步骤用 `for`、`match` 与 `let` |

注释写原因、约束与取舍。

## 测试

```text
for 每一项要保护的行为:
    if 类型或代码结构能保证:
        由结构保证，不写测试
    elif 属于核心业务逻辑或数据流:
        用单元测试或集成测试锁定
    elif 属于系统整体功能:
        用 E2E 或外置 harness fixture 验证，一个场景核对多处结果
```

- 断言写具体语义：结局、回执、持久记录与观察结果分别核对。
- 夹具与模拟组件按真实组件可能产生的状态与时序构造。
- 各层的入口、harness 与执行资源见[测试工程](testing.md)。

### TDD

1. 写一个测试，确认它因预期的原因失败。
2. 写最少的实现，让它通过。
3. 完成后清理这一轮留下的测试，优先删除：结构已经保证的、与其他测试重复的、只复述实现的。留下的测试符合上面的判定。

## 验证

1. 按影响范围选验证集：直接修改的模块，然后是受影响的调用方与接口，最后是必要的边界。
2. 纯文档修改：按[文档写作](../governance/writing.md#修改文档)检查，并核对内容、示例与 diff。
3. 全仓 CI、全量测试与黑盒测试用于跨组件、产品接线与外部可观察行为的变化；运行前写明它验证什么。
4. 同一时间运行一套重型验证，编译并发按机器资源设置；输入未变的检查沿用上次结果。
5. 报告实际执行的命令、结果与未验证的范围。远程 CI 与维护者审查照常进行。
