# ADR 0008：本地后台 API 分为命令、视图与查询

- 状态：Proposed（草案，待维护者裁决）
- 日期：2026-10-15
- 修订：部分取代 ADR 0006 第 4、10 节与 ADR 0007 第 8 节，范围见[与 ADR 0006、ADR 0007 的关系](#与-adr-0006adr-0007-的关系)
- 依赖：ADR 0007
- 实施跟踪：尚无 Issue（设计讨论见 #288）

## 背景

前端经本地后台读取会话内容。以下按 `main` 的 `cd5d97fc` 核对，此时 ADR 0007 已实施。

- **同一份内容有三种交付形状。** 事件（`TurnEvent`，每个正在执行的 Turn 在内存中保留最近 64 条）、快照（`ObservationSnapshot`）和历史（`HistoryEntry` 分页）在不同时期加入：2026-05 只有事件，运行时看事件、提交后看历史，两者不重叠；2026-09 后台成为独立进程，前端可以中途接入和重连，于是加入快照。自此三路在时间上重叠，同一个工具调用可以分别经事件、快照和历史到达。
- **合并由每个读者自己做。** 客户端库维护订阅游标、积压后丢弃事件再重新订阅、快照代次与历史锚点，向前端交付十种 `LocalUpdate`。TUI 按 UserMessage 的位置把旧显示并入新历史，工具块记录来源，Turn 结局按 TurnId 去重，重试提示按尝试去重，轮次序号自己数。#279、#281、#284 都出在这段合并代码里。CLI 的 `--json` 把收到的东西逐条打印，共 24 种记录，同一个结局可能出现多次，脚本要做与 TUI 相同的合并。
- **#289 留下两处过渡。** 重试等待写入节点后，历史条目带回重试提示，实时的 `LlmRetry` 事件仍在发，一直开着的客户端收到两遍；TUI 按尝试去重，CLI 在 `--verbose` 下打印两遍。快照的 `owned` 只回答所选 Turn，当前位置停在另一轮未关闭的 Step 上时，客户端判断不了那一轮是在执行还是执行者已消失，要先转去观察它。
- **历史读取没有按记录分页。** `history_page` 的分页只为适应 IPC 单帧上限：游标是锚点、节点与 UTF-8 偏移，小节点并在一页，大节点切成分片。客户端读完所有页才交给前端，打开会话总是读完整条路径；每读一页，后台都从锚点沿父链走回根。
- **请求身份分两处生成。** TurnId 由客户端生成，新会话的 SessionId 由后台在接受前生成、查重并占住，客户端要等接受回执才知道。会话合同因此另写了“不带 SessionId 的首次提交按 TurnId 找回”，TUI 也为“新会话首次提交尚无 SessionId”单列了提示。
- **提交兼做找回。** 同一 TurnId 重发时，`submit` 返回原 Turn；CLI 的 `--turn-id` 就是为此而设。为了让找回与 Busy 不必先加载凭据，提交前还有一次无配置探测：后台回答已有 Turn、Busy 或 `NeedsConfiguration`，客户端库为此维护共同惰性握手与一次性配置加载闭包，取消的接管规则和 CLI 的未提交状态（`not_sent`、`not_accepted`）也随之多出几种情况。
- **取消带一个只用于比对的字段。** `cancel` 的目标是 `{ turn_id, session_id }`，`turn_id` 已能唯一确定 Turn，`session_id` 只用来比对，CLI 因此要求 `session cancel <SESSION_ID> <TURN_ID>` 两个参数。

这些形状是不同时期叠加的结果，不是哪条需求要求的。ADR 0007 让会话事实只在节点上；本 ADR 让交付也只有一种形状。

## 决策

### 1. API 分为命令、视图与查询

| 类别 | 接口 | 说明 |
| --- | --- | --- |
| 命令 | `submit { turn_id, session: New(session_id) \| Existing(session_id), input, config }` | 接受一轮并执行；身份见第 6 节；TurnId 已被使用时返回 Conflict，见第 7 节 |
| | `cancel { turn_id }` | 取消一轮，返回是否接管，见第 8 节 |
| | `rewind { session_id, node_id }` | NodeId 是会话内序号，须与 `session_id` 一起定位 |
| 视图 | `watch { session_id }` | 推送这个会话现在的样子，见第 3 节 |
| 查询 | `history { session_id, before, turns }` | 取节点 `before` 之前的若干轮，见第 4 节 |
| | `turn { turn_id }` | 按 TurnId 读一轮，结果为已接受、在途或没有这个请求；接受结果不明时用它找回，见第 7 节 |
| | `list`、`log`、`audit` | 供 CLI 与操作员使用，不变 |

命令改变会话或执行，视图推送当前状态，查询读取已写入的事实。参数的取舍标准：定位所必需的字段保留，只交给后台核对的第二份去掉。

现有的 `query`、`subscribe`、`history_page`、事件流与 `LocalUpdate` 由上表取代。

### 2. 对话条目就是节点

视图与历史查询给出同一种对话条目。一个条目对应一个节点，以 NodeId 标识；同一节点的新值整条替换旧值。

- **UserMessage 条目**：节点本身，加上这一轮的轮次序号（见第 4 节）。agent 名、模型、provider 与执行限制已在节点上（ADR 0007 第 6 节）。
- **Step 条目**：节点本身，加上会话库从它得出的读取投影：各尝试、槽位与这一步的结论（ADR 0007 第 4 节的表）、各尝试的重试提示。这一步不是以 `Continue` 关闭时，它就是本轮的最后一步，条目另带这一轮的 `TurnSummary`。

一个 Step 就是一次模型调用及其引出的工具执行。`progress` 只有一份，结论由整个节点得出，它本身是完整的，所以不再拆成回复与各个调用：拆开之后前端要重新拼出这一步，后台要多一层映射，正是本 ADR 要去掉的合并。

结局只随本轮最后一步给出。除最后一步外，同一轮的 Step 都以 `Continue` 关闭，关闭后不再变化；结局放在最后一步，前面的步骤不必因后面的进展重推。以 `Continue` 关闭的那个事务同时预留下一步，两个节点都变了，所以都会推送：前一步不再带结局，新预留的一步带上。

重试提示是 Step 条目的一部分，不再有单独的事件。#289 留下的过渡去重随之删除。

### 3. 视图按会话推送“现在是什么”

`watch` 按会话观察，没有“所选 Turn”。它依次给出：

1. **会话头**：当前位置、当前 agent、当前位置所属的那一轮有没有 Owner，以及后台已知的这一轮执行诊断（例如因会话库写入失败未能关闭）。
2. **最近 N 轮**：当前路径上最近 N 轮的条目，按路径顺序排列；更早的用历史查询取。
3. **之后的变化**：变化的条目整条重推。当前位置沿路径前进时，只推新条目与会话头；当前位置移到别处（`rewind`）时，会话头标明路径已替换，随后给出新路径上最近 N 轮，客户端丢弃此前的条目。
4. **生成中的文字**：当前尝试正在生成的正文与 reasoning，标明所属节点与尝试。后台记录已发给这个观察者的位置，只发后面的部分。条目显示该尝试已 `Ended` 时，这些文字被条目取代：尝试完成时节点带有同一份完整回复，尝试停止时半截文字只作诊断。文字不进历史，不发给 provider。

后台为每个观察者记下哪些条目在上次推送之后变了，轮到推送时读出最新值发出。观察者变慢时只少收中间版本，同一节点收到的值只会更新、不会回退；赶上之后，它持有窗口内每个条目的最新值与最新的会话头。不需要事件窗口、事件游标与重新同步。

这一轮是否结束沿用 ADR 0007 第 8 节：最后一步的 `progress` 为 `Closed`，或者未关闭且会话头说明没有 Owner。会话空闲时没有推送是正常的；“长时间没有进展”的提示只在有 Owner 执行时适用。

### 4. 长会话按轮分页

`watch` 开始时只给最近 N 轮；往上翻时用历史查询取更早的轮。

- **按轮计数，不按大小。** 历史查询取节点 `before` 之前的 N 轮：后台沿 `before` 的父链往回收集节点，收到第 N 条 UserMessage 为止。页的边界只落在 UserMessage 之前，每页是完整的 Turn，不切节点，也不切 Turn。前端以整轮显示，USER、带轮次序号的标题线和结局行都属于一轮；按节点数切，页首会出现缺少 UserMessage 的半轮。
- **没有游标。** 参数只有 `session_id`、NodeId 与轮数。路径上已关闭的节点不再改变，一个节点之前的路径就是它的父链，当前位置改变后同一请求仍然有效。
- **轮次序号由后台给出。** UserMessage 的序号是它的祖先中 UserMessage 的个数加一。它只取决于固定的父链，读取时计算，不存入节点。

### 5. 大小交给连接层

一条消息超过 IPC 单帧（16 MiB）时，由连接层分帧发送，收齐后交给上层；API 与前端看不到分片。单次尝试的输出上限为 16 MiB，加上工具结果，Step 节点在极端情况下会超过单帧。

现有的字节分页、节点分片与 `HistoryCursor` 从 API 中删除。

每个槽位的进展都会让 Step 整条重推，回复随之重发。回复通常只有几 KB，先整条推，测出问题再优化。

### 6. 请求身份由客户端生成，后台校验

SessionId 与 TurnId 都由客户端在提交前生成，形状不变。提交时写明新建还是追加：`New(S)` 或 `Existing(S)`。不能以“这个 ID 不存在就新建”代替显式的新建，否则打错的会话 ID 会悄悄建出一个新会话。

后台生成、查重并占住 SessionId 的循环删除；“不带 SessionId 的首次提交按 TurnId 找回”与 TUI 的对应特例随之删除。

### 7. `submit` 只接受新请求，找回改为查询

`submit` 的职责是接受一轮并执行。TurnId 已被使用，就没有新的一轮可以执行，返回 Conflict；`submit` 不再兼做找回。

后台校验身份的形状（按现有的严格解析，不合格的在 IPC 解码时拒绝），再核对身份与库中事实是否相符，TurnId 先于会话核对；Conflict 带上原因，客户端据此区分：

| 请求 | 事实 | 结果 |
| --- | --- | --- |
| 任意 | TurnId 已在 TurnId 索引中，或另一个在途请求正在使用它 | Conflict：TurnId 已被使用 |
| `Existing(S)` | S 存在且项目绑定一致 | 接受；同 Session 有不同请求由 Owner 执行时返回 Busy |
| `Existing(S)` | S 不存在，或绑定不一致 | NotFound，或 Conflict：项目绑定不一致 |
| `New(S)` | S 不存在 | 在接受事务中建立 S |
| `New(S)` | S 已存在 | Conflict：会话已存在 |
| `New(S)` | 另一个在途请求已在准入阶段占住 S | Busy；对方被拒绝时 S 没有建立，重试可以成功 |

**找回改为查询。** 接受结果不明时（提交连接在回执到达前断开，或后台报告接受事务的 `commit` 结果不明），客户端按 TurnId 查询这一轮，结果是三种之一：

- **已接受**：返回这一轮，客户端接着 `watch`。
- **在途**：后台仍在准入这个请求，稍后再查；准入结束后变为另外两种之一。
- **没有这个请求**：确定未被接受，客户端保留输入，由用户决定是否重发。

后台读到提交请求时先登记在途的 TurnId（上表第一行用的也是这份登记），再确认提交连接仍在，连接已断开的请求不再准入。所以连接断开后查到的“没有”是终局，找回不需要以同一身份重新提交，也不会停在“仍然不明”。提交连接仍在且尚无回执时，客户端继续等回执，不查询。视图中出现该 TurnId 的 UserMessage，说明的是同一件事。

**删除无配置探测。** 探测是为了让找回与 Busy 不必先加载凭据。找回改为查询后，它只剩 Busy 一个用途，而加载 profile 与凭据只是读本地文件。客户端加载好配置后提交一次。`NeedsConfiguration`、共同惰性握手与一次性配置加载闭包删除；取消的接管规则中与无配置请求有关的情况，以及 CLI 的未提交状态 `not_sent`、`not_accepted`，随之删除。

### 8. 取消按 TurnId

`cancel` 只收 `turn_id`。取消的应是请求方看到的那一轮，而不是此刻恰好在执行的那一轮：请求方看着 T1 时，T1 可能刚结束，另一个客户端又在同一会话提交了 T2，按会话取消会取消 T2；按 TurnId 取消，后台发现 T1 已结束，返回未接管。

TurnId 由 TurnId 索引和准入状态唯一定位，`session_id` 只是核对用的第二份，删除。提交它的进程（TUI，或运行中的 `session send`）经自己的句柄按 TurnId 取消；取消意图、回执与退出交接的规则不变。

### 9. CLI

- **`--json` 的流式输出**只有以下记录：提交记录 `submit`、取消回执 `cancel`、会话头 `head`、对话条目 `entry`、生成中的文字 `text`，以及 `connection` 与 `error`。旧的事件行格式不保留。`submit` 在发出请求前输出一条，写明 TurnId 与 SessionId，收到回执后再输出一条，写明结果。读者按 `node` 覆盖 `entry` 即可；结局在本轮最后一个 Step 条目的 `TurnSummary` 中，不另加“结束”记录；退出码规则不变。
- **`session send --json` 只输出这一轮**：本轮的条目、会话头、文字与回执，不再输出整条路径的历史。`session turn --follow` 同样只输出所跟的那一轮。
- **删除 `session send` 的 `--turn-id`。** 找回不再由 `send` 负责，改用 `session turn <TURN_ID>` 查询。CLI 在发出请求前生成身份并先输出，脚本从第一条记录取得 TurnId 与 SessionId；进程在发送前被终止时，请求也没有发出。`lattice run` 与 `session send` 共用参数，一并删除。
- **暂不提供读取历史的 CLI 命令。**
- **`session cancel <SESSION_ID>`** 取消该会话当前正在执行的一轮。命令名指的是会话，参数就是会话：CLI 先从会话头查出那一轮的 TurnId，再按 TurnId 取消，输出写明取消的 TurnId；没有正在执行的一轮时报告无可取消。人在另一个终端里对一个会话说“停”，停掉的就是它此刻在执行的那一轮，第 8 节的竞态在这里不算问题。
- `list`、`log`、`turn`、`audit` 的 `--json` 不变。

### 10. 客户端保留的部分

- 连接后台，后台未运行时启动它。
- 读取 profile、系统提示与连接凭据，加载好之后提交一次。凭据来自前端进程的环境与 `.env`，`FrozenConfiguration::from_env` 不得由后台调用。
- 发出提交与取消，处理回执、取消意图与退出交接。接受结果不明时按第 7 节查询找回。
- 提示与后台的连接中断。
- 超过单帧的消息由连接层分帧与拼回。

订阅游标、积压后的重新订阅、快照代次与历史锚点、历史分页与分片拼回，以及三路内容的合并，从客户端删除。

前端只保存正在显示的条目，同一 NodeId 新值替换旧值；往上翻到已装入的最早一轮时，用历史查询取更早的轮。另有输入、排队、评论草稿、滚动位置等自身状态。TUI 的位置合并、工具来源标记、两处去重与轮次序号计数随之删除。

### 11. 协议版本

IPC 协议版本升级（`LTLOCAL3` 改为 `LTLOCAL4`），新旧客户端与后台沿用现有的版本校验互相拒绝，不做兼容层。

### 12. 合同先行

沿用 ADR 0007 第 11 节：会话合同与 TUI 合同按本 ADR 修订后先行合并，实现随后跟上。合同合并到实现完成之间，两份合同描述目标行为，与当前代码不一致。

### 13. 验证方式

- **视图**：中途开始的观察、变慢的观察者、空闲时 `rewind` 替换路径、Turn 关闭与最后一次推送同时就绪，各情况下观察者最后持有的条目与关闭后用历史查询重读的一致；生成中的文字与最终回复的正文合并相邻同类后相同。
- **重开一致**：实时观察与重新打开会话看到的条目相同，包括重试提示；执行者消失后重新打开，会话头直接说明没有 Owner。
- **分页**：页的边界只落在 UserMessage 之前；轮次序号与从根数起的结果相同；当前位置改变后同一历史查询结果不变。
- **提交与找回**：第 7 节表中的每一行各有场景；查询的三种结果各有场景，包括原请求仍在准入时得到在途，以及后台尚未开始准入时连接断开、请求不再被接受。
- **CLI**：`--json` 只出现第 9 节的记录类型，第一条是写明身份的 `submit`；`session send --json` 只输出本轮；`session cancel <SESSION_ID>` 取消正在执行的一轮，没有时报告无可取消。

## 与 ADR 0006、ADR 0007 的关系

| 章节 | 本 ADR 后的状态 |
| --- | --- |
| ADR 0006 §4 会话操作 | 部分取代：`session send` 不带 `--session` 时，新会话的 SessionId 由客户端生成，提交写明新建，见第 6 节；“同一 `--turn-id` 重发找回原请求”取代为按 TurnId 查询，`--turn-id` 删除，见第 7、9 节；`session cancel` 的参数改为 `<SESSION_ID>`，见第 9 节；其余保留 |
| ADR 0006 §10 观察与订阅 | 部分取代：事件窗口、事件游标、“快照 + 按序事件 + 结束”与重新同步由按会话的视图取代。段列表保留，作为生成中的文字的来源；顺序保留与跨 provider 两条保留；完成确认一条保留，其中“由同一 `--turn-id` 重发找回”改为按 TurnId 查询 |
| ADR 0007 §8 读取时带上 `progress` | `TurnSummary` 的解读规则保留。“历史读取为每个带有等待时长的尝试带回一条提示”改为重试提示是 Step 条目的一部分；“当前位置是未关闭的 Step 时随快照交付、不经历史分页”改为它随视图推送，历史查询只取更早的轮 |
| ADR 0007“不在本文决定的事项”中的 #288 | 由本 ADR 回答：未关闭且没有 Owner 的 Turn 由会话头说明；重试提示随 Step 条目给出；模型与 provider 随 UserMessage 条目给出；#284 的位置推断随按 NodeId 替换删除 |

ADR 0006 与 ADR 0007 的正文保留。

## 后果

好处：

- 前端不再合并。只有一种条目，按 NodeId 替换；#279、#281、#284 所在的合并代码删除，TUI 与 CLI 的去重也一起删除。
- 实时观察与重新打开会话看到的是同一种条目，重试提示也在其中。
- 慢观察者不需要重新同步，后台没有事件窗口，客户端没有事件游标。
- 打开长会话只读最近 N 轮。
- 判断执行者是否消失不再需要先观察那一轮。
- `--json` 的记录类型从 24 种减到 7 种，脚本按 `node` 覆盖即可。
- 新会话从提交起就有 SessionId，请求找回不再有特例。
- `submit` 只接受新请求，提交前没有探测，客户端库少了一套握手；取消的接管规则与 CLI 的未提交状态随之变少。

代价与风险：

- 后台为每个观察者保存待推送的条目集合与文字位置，内存随观察者数增长，受现有订阅许可（32）约束。按观察者推送最新值，Codex app-server 与 Claude Agent SDK 都没有先例（对照见 #288）。
- 每次推进整条重推 Step，回复随之重发。
- 极端大的 Step 节点要跨多帧，连接层要实现分帧与拼回。
- 轮次序号每次读取都要沿父链数祖先，代价与路径深度成正比。现在的历史分页每页也要走一遍父链，量级相同。
- 接受结果不明时要多一次查询；原请求仍在准入时要稍后再查。
- 不兼容：IPC 协议、公开 DTO、CLI `--json` 与 `session send` 的参数都改变。`lattice-system-harness` 中按事件行断言、靠 `--turn-id` 预定身份或靠重发找回的场景要重写，外部脚本要改。
- SessionId 的唯一性依赖客户端生成的随机值，碰撞或重复使用由第 7 节的校验拦下。
- 会话合同与 TUI 合同中观察、重连、取消与重载的章节大幅修订。

## 否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 保留事件、快照与历史三路，只统一条目形状（Codex app-server 的做法） | 前端仍要处理三路到达的先后与重复，重连仍要重新同步 |
| 回复与每个工具调用各为一个条目（Codex 的 item 粒度） | 本项目的存储单位是节点；拆开要前端重新拼出一步、后台多一层映射 |
| 结局随 UserMessage 条目或每个 Step 条目给出 | 前者每次推进都要重推用户输入；后者前面的步骤要随后面的进展重推，或者带着过时的值 |
| 按字节分页，大节点在 API 中分片 | 大小已由连接层分帧负责，两层重复计量；分片要带游标，当前位置改变后失效 |
| 按节点数分页 | 页首可能是缺少 UserMessage 的半轮，没有序号与标题线 |
| 分页带游标 | 已关闭的节点不变，NodeId 已足够定位 |
| `watch` 一次给出整条路径 | 长会话打开慢，客户端要持有全部条目 |
| 轮次序号存入节点 | 可由父链得出；存了就要核对 |
| `--json` 保留事件行 | 脚本要做与 TUI 相同的合并 |
| `--json` 另加“结束”记录 | 与最后一步的 `TurnSummary` 重复 |
| API 的 `cancel` 按会话 | 可能取消请求方没有看到的那一轮 |
| CLI 的 `session cancel` 只收 TurnId | 命令名指会话，参数却是一轮，有歧义；人在终端里通常只知道会话 |
| 后台生成 SessionId | 新会话在接受前没有 SessionId，要按 TurnId 找回的特例 |
| 会话 ID 不存在就新建 | 打错的会话 ID 会悄悄建出新会话 |
| `submit` 对已用的 TurnId 按找回处理，返回原 Turn | `submit` 是接受并执行的命令，兼做找回就是在写操作里做读；会话已有后续各轮时，找回的那一轮也无从执行 |
| 找回的查询只分查到与查不到，查不到时以同一身份重新提交 | 查不到也可能是原请求仍在准入，只能靠重新提交得到的 Conflict 区分，到期仍分不清时又回到结果不明 |
| 保留 `session send --turn-id` | 找回不再由 `send` 负责；CLI 在发出请求前已输出身份 |
| 保留无配置探测 | 找回改为查询后只剩 Busy 一个用途，加载配置只是读本地文件 |
