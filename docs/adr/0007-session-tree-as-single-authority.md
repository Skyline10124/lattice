# ADR 0007：会话树作为会话事实的唯一权威

- 状态：Proposed（草案，待维护者裁决）
- 日期：2026-10-12
- 修订：部分取代 ADR 0006，范围见[与 ADR 0006 的关系](#与-adr-0006-的关系)
- 依赖：ADR 0006 未被取代的部分
- 实施跟踪：尚无 Issue

## 背景

ADR 0006 把一个会话的事实分成三层保存：树节点保存对话内容，Step 记录保存每次模型请求和结束方式，Turn 记录保存冻结配置与结局。一个 Step 只有在全部调用都有结果之后才写入树，进行中的内容放在 ActiveStep 里。

这个划分带来几个后果，以下按 `main` 的 `190ffb9e` 核对。

- **同一个会话，实时看到的和重新打开后读到的不是同一处。** 历史读取只带回树节点。失败后被重试的模型请求只记在 Step 记录里，重新打开会话后看不到重试提示；实时观察时这些提示来自事件。TUI 因此要在装入历史时把实时内容和历史内容拼在一起，并推断它们的相对位置。#279 记录了由此产生的错位与误去重；#281 让结局行由历史带回之后出现过顺序回退，#284 以位置推断作了临时修复。
- **没有产生回复的步骤不在树上。** 一个 Turn 在得到任何回复之前失败或被取消时，Step 记录以 `Stop { node: None }` 结束，树上只有它的 UserMessage。
- **进程退出后要先补写。** 崩溃时 ActiveStep 里可能有没有结果的调用和没有终态的尝试。后台在该 Session 下一次写操作之前执行自动关闭，把它们补成 NotExecuted、`Indeterminate(NoResult)` 和 `Stopped { ProcessExit }`。为此 Session 记录保存“进行中 Turn”标记，会话库在这个标记存在时拒绝接受与退回，并返回 `RecoveryRequired`。不算测试，`active_turn` 在 9 个文件中有 25 处引用，自动关闭在 7 个文件中有 17 处。
- **同一事实保存两份。** Turn 的结局与 notice 由最后一个 Step 派生，又存入 Turn 记录，读取校验要重新推导并比对。已关闭的 Step 记录保存各调用的终态，Step 节点保存同一批结果。

#279 的第一种修法是历史读取时从 Step 记录投影出重试列表。它实现并验证通过，但事实仍然分存两处，只是在读取时拼起来，维护者据此指出它只是变通做法。讨论的结论是先回答“哪一处是会话事实的权威”：如果树是权威，树上就必须有全部事实；如果树只用于导航，就必须另有一处唯一的权威。本 ADR 选择前者。

## 决策

### 1. 树是会话事实的唯一权威

一个会话里发生过什么，以树上的节点为准。后台为这个会话提交的每一件事都写在节点上：每次模型请求及其结果、完整回复、每个工具调用及其结果、每一步如何结束。其他记录只有三种地位：节点的一部分（Turn 记录）、指针（Session 记录中的当前位置），以及从节点得出的索引（InvocationId 索引、调用变更日志）。

读取投影从节点得出，不另存：Turn 的结局、notice、usage 汇总、结束时间，以及历史中的重试提示。

### 2. 从属关系写在节点上，分叉只来自 rewind

父子关系只表示先后。节点属于哪个 Turn、是第几步，由节点上的 `turn_id` 和步骤序号表达。尝试和工具调用属于某个 Step，所以保存在 Step 节点内部，不各占一个节点。

用子节点或分支表达从属，会和这棵树已有的两种含义混在一起：链式的对话顺序，以及 `rewind` 产生的分叉。读者将无法只凭树形判断一个分叉是另一种后续，还是同一步的另一次尝试。

### 3. Step 节点在开始之前预留

接受一轮的事务写入 UserMessage，同时预留第 0 步；一个 Step 以 `Continue` 关闭时，同一事务预留下一步。预留的 Step 没有尝试和回复。Turn 以完成或停止结束时不再预留，也没有单独的结束节点。

这样每一步从开始就有节点可写，没有产生回复的步骤也留在树上。同一 Turn 的节点序号因此连续：UserMessage 之后依次是各个 Step。

### 4. `progress` 与预写的结论

Step、尝试和调用槽位各保存两项，总在同一事务中一起写入。

- `progress` 是最后到达的阶段。它只前进，不因关闭、取消或进程退出而改动。
- 结论是停在这个阶段时的结果。到达一个阶段就写下它对应的结论，阶段前进或实际结果到达时覆写。

| 对象 | `progress` | 此时的结论 |
| --- | --- | --- |
| Step | 已预留、请求中 | 停止，原因为进程退出 |
| Step | 执行中 | 停止，原因由各槽位的结果推出，推不出时为进程退出 |
| Step | 已关闭 | 继续、完成，或停止及实际原因 |
| 尝试 | 已发出 | 停止，原因为进程退出 |
| 尝试 | 已结束 | 完成，或停止及实际原因与诊断 |
| 调用槽位 | 已登记 | NotExecuted |
| 调用槽位 | 已开始 | `Indeterminate(NoResult)` |
| 调用槽位 | 已返回 | LANCET 给出的结果 |

这些预写的值与 ADR 0006 的自动关闭补写的值相同。它们只取决于“最后到达哪个阶段”，所以可以在到达时写下，不必等到崩溃之后。树上因此任何时刻都没有空缺；执行者在任何时刻消失，已有的内容就是这一轮的结局。

树只追加节点。可以改写的节点至多一个：Session 中序号最大的节点，且它是未关闭的 Step。

### 5. 取消自动关闭和“进行中 Turn”标记

预写之后，自动关闭没有可写的内容，连同以下各项一起删除：Session 记录的“进行中 Turn”、关闭规划、会话库在接受与退回时返回的 `RecoveryRequired`，以及提交握手中“先关闭旧 Turn 再继续”的步骤。

一个未关闭的 Step 可能仍在执行，也可能执行者已经消失。两种情况在树上相同，由后台区分：会话库只由持有实例锁的后台进程打开，执行一个 Turn 需要后台内存中的 Owner 和该 Session 的执行锁，所以后台没有某个 Turn 的 Owner 时，没有人在执行它。执行者消失后，用户直接提交新请求或 `rewind`，旧 Turn 的节点保持原样。

正常关闭仍由关闭事务和关闭事件确认，只有执行者消失的情况依赖上述判断。

### 6. Turn 记录只保留接受部分

Turn 记录保存接受一轮时确定的事实：所属 Session、UserMessage 节点序号、冻结配置及其摘要、接受时间。它与 UserMessage 节点同事务写入，此后不修改，同时用于按 TurnId 找回请求。它是 UserMessage 节点的一部分，单独存放是因为冻结配置可达数 MiB（系统提示上限 2 MiB，工具目录上限 1 MiB），而读取对话路径要逐个解码节点。

Turn 记录不再保存原始输入和项目绑定的副本，也不保存结局、notice、usage 汇总和结束时间。

### 7. 每次推进记录时间

Step 节点保存最后一次推进的时间。Turn 关闭时，它就是结束时间；Turn 没有关闭时，它说明这一轮最后一次有进展是什么时候。执行者消失的 Turn 因此也有可读的时间，不需要事后写入。

### 8. 读取时带上 `progress`

公开读取投影为 `TurnSummary { outcome, notice, progress }`，任何时候都有值。读者按 `progress` 和后台是否持有 Owner 解读 `outcome`：

- 已关闭：最终结局。
- 未关闭，有 Owner：仍在执行，`outcome` 只说明此刻停下会得到什么。
- 未关闭，没有 Owner：执行者已消失，`outcome` 就是结局。

失败的尝试被安排重试时，等待时长与终态同事务写在这次尝试上。历史读取为每个带有等待时长的尝试带回一条提示，内容与实时发出的 `LlmRetry` 相同。当前位置是未关闭的 Step 时，这个节点随快照交付，不经历史分页读取，因为它还可能被改写。

### 9. 旧数据

节点的值格式改变，Step 记录表删除，Turn 记录缩减。建议沿用 ADR 0006 第 2 节的做法：会话库的格式版本升级，旧库打开失败并指出路径，不迁移。这一条须由维护者明确授权，见[待定事项](#待定事项)。

### 10. 验证方式

沿用 ADR 0006 第 11 节，崩溃场景的核验内容调整为：在每个提交点 SIGKILL 后重开，先不做任何写入，核验每个槽位都有结果、每次尝试都有终态、每个 Step 都有结束方式，且都与各自的 `progress` 相符；随后核验 `send` 与 `rewind` 直接成功，旧 Turn 的节点保持原样。

## 后果

好处：

- 重新打开会话读到的内容与实时看到的来自同一处。失败的尝试和没有产生回复的步骤都在树上，#279 的两种表现由此消除，#284 的位置推断可以删除。
- 没有恢复路径。自动关闭、“进行中 Turn”标记和相应的 `RecoveryRequired` 连同它们的测试一起删除；提交与退回不再有前置步骤。
- 结局只有一个来源。Turn 记录与最后一个 Step 之间、Step 记录与 Step 节点之间的一致性校验消失。
- “执行者何时消失不改变结局”仍然成立，并且不再依赖事后补写。

代价与风险：

- 树不再是只追加的：末端未关闭的 Step 会被改写。读者要按 `progress` 和 Owner 解读它，历史分页要避开它。
- 执行者消失的 Turn 永久停在未关闭状态。把它当作已经结束，依赖“会话库只有一个后台进程写入”这一条；多进程访问会话库本来不在范围内，今后若要支持，这一条须重新设计。
- 每次推进重写整个 Step 节点，其中包括完整回复和已有的槽位结果。现在每次槽位变化同样重写整条 Step 记录，量级相同。
- 操作员读到的调用状态带有预写的结果，`audit --tail` 不再出现关闭时补写的那些行。操作员接口的表达要随之调整。
- 存储格式改变，旧会话库不可读。
- 实施量大。会话库模块约五千行、测试近三千行，其中的记录类型、写入、关闭和校验大半要重写；读取与观察的 DTO、TUI 与 CLI 的历史装载、操作员接口和崩溃场景测试都要跟着改。

## 否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 历史读取时从 Step 记录投影重试列表 | 实现并验证通过，但事实仍分存两处，只在读取时拼接；每多一类要显示的事实就要多一个投影 |
| 在树上增加 Notice 或日志节点 | 提示是某次尝试的属性，不是独立的对话内容。以“是否需要持久化”判断什么进节点，回答不了“重试之后成功了，那条提示还要不要” |
| 每次尝试、每个工具结果各占一个节点 | 父子关系表示先后；用它表达从属会与对话顺序和 `rewind` 的分叉混淆。ADR 0006 已否决独立的工具结果节点 |
| 保留三层记录，把树只当作导航 | 需要另有一处唯一的权威，并保证树与它一致；现状是两处各记一部分 |
| 结论留空，由读者在读取时推断 | 每个读者都要实现同一套推断规则；空值本身不说明停在这里意味着什么 |
| 关闭或崩溃之后把 `progress` 标成最终 | 崩溃之后没有执行者来写这个标记；需要事后写入就回到了自动关闭 |
| 保留自动关闭，只把它的结果写进节点 | 预写之后自动关闭没有可写的内容，却仍要保留标记、规划和前置步骤 |
| 预写日志或只追加的事件日志 | redb 的事务已提供原子提交。工具调用和模型请求不能重做也不能撤销，崩溃后能做的只有写下结论，而结论可以预先确定。只追加的日志还要求每个读者自行折叠出当前状态 |
| Turn 结束时写一个结束节点 | 最后一个 Step 的结束方式已经说明结局；多一个节点就多一处要保持一致的内容 |
| 把冻结配置放进 UserMessage 节点的值里 | 读取对话路径要逐个解码节点，每个 Turn 会多解码可达数 MiB、读取对话时用不到的内容 |

## 待定事项

需要维护者裁决：

1. **接受时确定的事实放在哪里。** 本 ADR 的写法是“属于 UserMessage 节点，另存为按 TurnId 存放的 Turn 记录”。另一种是放进节点的值里，接受读取时的解码成本，或为节点的值设计分段解码。
2. **阶段的名称。** Step 为已预留、请求中、执行中、已关闭；尝试为已发出、已结束；调用槽位为已登记、已开始、已返回。代码中的标识符在实施时确定。
3. **`rewind` 是否记入树。** 本 ADR 保持现状：`rewind` 只移动当前位置，不写节点，它发生的时间只反映在 Session 记录的更新时间上。
4. **调用变更日志。** 本 ADR 把它保留为派生记录，每次槽位 `progress` 前进追加一行。操作员接口如何表达“阶段加预写的结果”，在修订 LANCET 合同时确定。
5. **旧数据。** 是否沿用“升级格式版本，旧库打开失败，不迁移”。
6. **合同与实现的先后。** 会话合同的修订可以先合并，实现随后跟上；也可以与实现在同一 PR 中合并。先合并时，合同会在一段时间内领先于代码。

随本 ADR 一并处理、但不在本文决定：

- #117：历史读取给出 result Cell 的形态。
- TUI 合同：未关闭且没有 Owner 的 Turn 如何显示，历史中重试提示的文字，以及删除 #284 的位置推断。
- LANCET 合同、存储合同与开发文档中提到自动关闭的各处。
