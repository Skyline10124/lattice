# 重开、取消与未完成状态

> 所属领域：[会话与 Turn](README.md)

## 请求身份与找回

客户端在提交前生成 TurnId，向已存在的会话 `SessionId` 发起 `submit`（携带 `input`、规范工作区与可选的 `expected_settings`）。新会话先通过 `configure(New)` 显式创建；`submit` 遇到不存在的会话 ID 时返回 NotFound，不会创建新会话。新 TurnId 表示独立请求，即使文本相同。

`submit` 只接受新请求。后台按严格解析校验身份的形状，不合格的在 IPC 解码时拒绝，下表列出提交时可能遇到的事实以及后台与前端的动作，后台检查的顺序见[实现模块与公开操作](operations.md#实现模块与公开操作)；Conflict 带上原因码（全系统共四种：`turn_id_used`、`session_exists`、`binding_mismatch`、`settings_changed`，其中 `session_exists` 只由 `configure(New)` 返回），前端据此区分：

| 提交时找到的事实 | 后台与前端动作 |
| --- | --- |
| TurnId 正在被另一个在途请求使用，或已在 TurnId 索引中 | 返回 Conflict：`turn_id_used` |
| 会话库尚未初始化，或会话 `S` 不存在 | 返回 NotFound |
| 会话 `S` 的 `project_path` 与请求工作区不一致 | 返回 Conflict：`binding_mismatch` |
| 全局 Owner 已满 32、同会话已有 Owner，或 `SessionExecutionLock` 被占用 | 非阻塞返回 Busy；前端保留未提交输入，由用户稍后发送 |
| 请求给出了 `expected_settings`，且与当前会话设置的 `SettingsVersion` 不等 | 返回 Conflict：`settings_changed`；前端保留未提交输入并以最新会话头为准，由用户核对当前设置后再发送 |
| Session 最后一轮未关闭，且没有 Owner | 旧 Turn 停在已写入的进度，不需要处理；直接接受本次新输入，见[执行者消失后的 Turn](#执行者消失后的-turn) |
| 以上都不是 | 从当前会话设置冻结本轮配置，在接受事务中追加本轮节点并返回接受回执 |

“接受结果未知”有三种来源：提交连接在回执到达前断开；后台报告接受事务的 `commit` 结果不明；接受事务已提交，后台却没能给出接受回执（读回这一轮失败，或转交回执时出错）。后两种由后台立即回复结果不明，不等这一轮执行完。这时 LocalTurn 按 TurnId 查询这一轮（`turn`），结果是三种之一：

| 查询结果 | 含义与动作 |
| --- | --- |
| 已接受 | 返回这一轮；后台仍在执行它时继续观察 |
| 在途 | 后台仍在准入这个请求；稍后再查，准入结束后变为另外两种之一 |
| NotFound | 确定未被接受；前端保留输入，由用户决定是否重发 |

后台读到提交请求时先登记在途的 TurnId，上表第一行的在途 Conflict 用的也是这份登记；随后确认提交连接仍在，连接已断开的请求直接终止准入。所以连接断开后查到的 NotFound 是终局，找回不需要以同一身份重新提交。后台也可能在连接断开之后才读到请求：它照样先登记为在途，随即因连接已断开而终止准入，所以 NotFound 之后的查询可能短暂为在途，但这个请求不会再被接受。提交连接仍在且尚无回执时，LocalTurn 继续等回执，不查询。视图中出现该 TurnId 的 UserMessage，同样说明已接受。退回操作不释放已用的 TurnId。请求找回保证不扩展为 Tool exactly-once。

执行核心分别给出接受结果、完成结果与推进通知；测试使用的 `run_turn` 复用该核心，同样要取得独立的 completion。Backend 在 Owner 退场后保存本进程已知的执行诊断，例如因会话库写入失败未能关闭 Turn，由视图的会话头给出；未经核验的请求冲突不覆盖原 Turn 的诊断。

## configure 的找回

- **幂等。** `configure` 是幂等的，见[并发、找回与生命周期](settings.md#并发找回与生命周期)。以同一参数重发是安全的：
  - 对已存在的 `S` 执行 `configure(New)`，返回 `session_exists`，重发方由此知道上一次请求已经建好 `S`；
  - Busy 表示会话或全局槽位正被占用，稍后再发。
- **CLI。** 只发一次 `configure`：
  - 无法建立连接，或后台明确拒绝：结果为 `rejected`。
  - 结果不明：结果为 `unknown`，输出 `configure` 的 `unknown` 记录与 `submit` 的 `not_accepted` 回执，退出 1。结果不明包括四种情况：写出请求时连接中断、读不到回复、后台回复 `Internal` 错误或恢复原因为 `CommitFailed`、`WorkerFailed` 的错误、`configure` 期间收到 SIGINT。
  - 结果不明之后由用户重跑命令。带 `--session S` 重跑，执行幂等的 `configure(Existing)`；不带 `--session` 重跑，会创建新会话，丢失请求可能留下的草稿会话由[草稿清理](concurrency.md#会话状态与草稿清理)删除。
- **TUI。** 只发一次 `configure`：结果不明时显示 Warn，实际生效的设置以 `watch` 推送的会话头为准，见 [TUI 合同](../tui/README.md#configure-结果不明与设置同步)。

## 观察与重连

普通退出释放客户端和观察连接，后台继续执行。前端以 `watch` 观察一个会话，重新连接就是重新开始 `watch`；活跃的观察连接同时保护[草稿会话](concurrency.md#会话状态与草稿清理)不被逾期清理。视图、历史查询和后台启动都不写会话库。

视图按会话推送这个会话现在的样子，没有“所选 Turn”。它依次给出：

1. **会话头**：完整字段清单与含义见[实现模块与公开操作](operations.md#实现模块与公开操作)；`configure` 更新会话设置后，观察者收到新的会话头。
2. **最近几轮**：当前路径上最近 10 轮（[`WATCH_TURNS`](../../../crates/lattice-api/src/local/types.rs)）的对话条目，按路径顺序排列；更早的用历史查询取。
3. **之后的变化**：变化的条目整条重推。当前位置沿路径前进时，只推新条目与会话头；当前位置移到别处（`rewind`）时，会话头标明路径已替换，随后给出新路径上最近 10 轮，前端丢弃此前的条目。
4. **生成中的文字**：当前尝试正在生成的正文与 reasoning，见下文。

**对话条目。** 一个条目对应一个节点，以 NodeId 标识；视图与历史查询给出同一种条目，同一节点的新值整条替换旧值。

- UserMessage 条目带这一轮的轮次序号：它的祖先中 UserMessage 的个数加一。序号只取决于固定的父链，读取时计算，不存入节点。agent 名、模型、provider、推理档位与执行限制在节点上。
- Step 条目带会话库从它得出的读取投影：各尝试（含用量与保存的费用估算）、槽位与这一步的结论（见[预留、progress 与结论](README.md#预留progress-与结论)），以及安排过重试的尝试的重试提示。这一步不以 `Continue` 关闭时就是本轮最后一步，条目另带这一轮的 `TurnSummary`。前面的步骤以 `Continue` 关闭后保持不变，结局只随最后一步给出；以 `Continue` 关闭并预留下一步的事务改了两个节点，两个条目都会推送。

**生成中的文字。** 每个正在执行的 Turn 在 Owner 的内存中保留当前尝试的段列表：当前模型尝试已发出的正文与 reasoning delta，按到达顺序记为 `(类型, 文字)` 段，相邻同类合并。新尝试开始时清空，完整回复写入 Step 节点后交由节点承载，Turn 关闭后释放。视图把它作为生成中的文字推送，标明所属节点与尝试序号；后台记录已发给每个观察者的位置，只发后面的部分。条目显示该尝试已 `Ended` 时，这些文字由条目接替：尝试完成时节点带有同一份完整回复，尝试停止时半截文字作废。前端保留已显示的临时文字，直到对应 Step 条目的回复实际装入显示，再原位替换。

一致性要求：当前尝试的段列表与最终 Step 节点的正文/reasoning parts，合并相邻同类后序列相同，回复切换为节点内容时显示不跳变。段列表只用于显示，不进历史、不发给 provider。

**推送。**

- 后台为每个观察者记下哪些条目在上次推送之后变了，轮到推送时从会话库读出最新值发出。观察者变慢时只少收中间版本：同一节点收到的值只会更新、不会回退；赶上之后，它持有已收到的每个条目的最新值与最新的会话头。读得慢不会丢内容，也不需要重新同步。
- 只有生成中的文字变化时，推送只含文字。会话头只在视图开头、路径替换之后、有变化的条目要推，或会话头本身变化（例如会话设置更新、Owner 退场、出现执行诊断）时推出。
- 后台每推一条会话头，同一次推送里接着给出当前位置的条目（当前位置是根节点时除外），即使它没有变化。视图没有批次结束标记，读者无从知道一次推送的条目是否已给完；会话头与随后的当前位置条目出自同一个读事务，所以读者判断这一轮是否结束（尤其是未关闭而没有 Owner）时，以收到最新会话头之后的当前位置条目为准，不拿新会话头配旧条目。
- Owner 先提交会话库事务，再在观察锁内更新段列表并标记变化的条目，例如新尝试开始时清空段列表。推送在观察锁内只复制段列表中尚未发给这个观察者的部分，再开启会话库读事务读出条目，所以文字所属的尝试一定已在条目中。读事务还可能多含一次刚提交、尚未标记的提交，之后对同一节点的推送给出同一个值，前端替换后显示不变。

**这一轮是否结束。** 最后一步的 `progress` 为 `Closed`，或者它未关闭且会话头说明没有 Owner，见[执行者消失后的 Turn](#执行者消失后的-turn)。会话头所示当前位置属于别的轮时，所跟的这一轮也已不在执行，按已结束处理：同一会话同时只执行一轮，执行中 `rewind` 与新提交都返回 Busy，所以正在执行的那一轮一定在当前位置。视图本身不结束，由前端决定何时停止观察；CLI 跟随一轮时，这一轮结束即停止。会话空闲时没有推送是正常的。

**后台重启。** 段列表与观察者的推送状态随进程消失，未关闭的 Turn 停在已写入的进度。客户端重连后重新开始 `watch`：会话头说明没有 Owner，条目说明它停在哪个阶段和结局。丢失的只有当时正在生成的半截文字，它本就不保存。

**读取更早的对话。** 历史查询 `history { session_id, before, turns }` 取节点 `before` 之前的若干轮：后台沿 `before` 的父链往回收集节点，收到第 `turns` 条 UserMessage 为止。页的边界只落在 UserMessage 之前，每页是完整的 Turn，不切节点。“完整”指所选父链上这一轮的内容：退回到一轮中途的 Step 再追加时，新分支上那一轮只有退回点之前的部分，分页保持它完整而不切开。没有游标：路径上已关闭的节点保持不变，一个节点之前的路径就是它的父链，当前位置改变后同一请求仍然有效。前端往上翻到已装入的最早一轮时，以它的 UserMessage 为 `before` 继续取，默认每次取 10 轮（[`HISTORY_TURNS`](../../../crates/lattice-api/src/local/types.rs)），每次最多 100 轮（[`MAX_HISTORY_TURNS`](../../../crates/lattice-api/src/local/types.rs)）。

CLI 的人类可读输出在一轮结束时打印一次结局摘要；`--json` 的记录见[实现模块与公开操作](operations.md#实现模块与公开操作)。CLI 按最终结局与执行诊断选择退出码；最终仍读不到内容或核验发现数据损坏时退出 1，不因已知 Completed 而忽略失败。工具按 InvocationId 配对显示，规则见 [TUI 对话记录与工具显示](../tui/transcript.md#对话记录与工具显示)。

### 观察边界

视图推送非阻塞，慢读、断连及 idle timeout 只结束或降级观察，不中止执行和必要持久收尾。视图与历史查询只读：不写会话库、不请求模型、不分发 Tool、不公开冻结配置中的秘密。

单个 IPC 帧有界。超过单帧的消息由连接层分帧发送，收齐后交给上层，API 与前端看不到分片；传输上限不能拒绝原本合法的整个 Turn 的内容。有界帧不代表固定内存：单个节点在读取时整体解码。拼回的整条消息不设总量上限：一轮最多 32 个 Step（模型步骤上限），每次回复最多 16 MiB，单是回复就可达 512 MiB，一次 `history` 又最多取 100 轮。能容纳全部合法内容的总量上限要以数十 GiB 计，超出客户端可用内存，起不到保护作用。

## 取消与退出

取消按 TurnId 进行：取消的是请求方看到的那一轮，而不是此刻恰好在执行的那一轮。请求方看着 T1 时，T1 可能刚结束，另一个客户端又在同一会话提交了 T2；按 TurnId 取消，后台发现 T1 已结束，返回未接管，不会取消 T2。

用户选择取消后，前端调用 LocalTurn 的 `cancel`，同步登记原 TurnId 的意图。LocalTurn 独立处理在途提交与取消回执；视图的读取和 UI 更新队列不承担控制状态。独立的 `session cancel <SESSION_ID>` 先从会话头查出该会话正在执行的那一轮，再按 TurnId 取消，直接取得后台接管结果。

### 后台接管与责任区间

Backend 以实际接管的操作确定取消资格。新建带完整配置的 Submit Owner 时，即在工作区 I/O、配置核验和执行核心创建前建立取消载体，向核心传递同一载体。取消的目标查找、资格核对和置位与 Owner 移除在同一准入临界区完成；监督者持有独立 completion，等待必要收尾后才移除 Owner。

| 判定点的事实 | 动作与回执含义 |
| --- | --- |
| 原目标的操作已被实际接管 | 置位同一取消载体并返回 true；重复请求幂等，后台独立处理至完成或明确诊断，连接退出不撤销责任 |
| 没有可接管取消的对应操作 | 查询原持久事实后返回 false，查询错误仍返回错误；false 仅表示判定点未接管，不证明后来不会接受同身份请求。执行者已消失的 Turn 不接受取消，它的结局已在树上 |
| 请求传输失败或回执丢失、超时 | 客户端报告 Unknown，保留原身份及其他已知事实 |

操作明确拒绝、可确认未建立 Turn 且监督退场后，同一 TurnId 的重新提交不继承旧取消，包括早已到达、此时才重新准入的连接。接受结果未知时按 TurnId 查询，不归入这类明确拒绝。

### 客户端意图与退出交接

LocalTurn 将取消显示为 Pending、Taken、NotTaken、Unknown 或 Moot，分别表示等待回执、已接管、判定点未接管、回执未知及无需继续交接。原目标尚未关闭、取消尚未接管且无在途 Cancel 时，首次 false 或传输未知与视图中同目标已被接受、仍有 Owner 的证据结合，最多触发一次补发；两种回执先后顺序共用该额度。

true 后由后台履行责任，不自动补发；再次明确取消可开始新额度，旧在途回执不充当新意图回执。后台明确拒绝本次操作或原目标已关闭时结束后续补发，已知 Taken 与真实结果分别保留；新请求的取消不转给同一 Session 中执行者已消失的旧 Turn。

取消发生在提交发出之前时，本客户端取消发送这次提交，没有需要交接的回执。

首次取消时若提交仍在途，LocalTurn 按[回执等待预算](concurrency.md#输入与传输限制)等待；到期报告提交结果不明，保留原提交任务接收迟到回执，视图照常推进；提交连接断开后才按 TurnId 查询找回，见[请求身份与找回](#请求身份与找回)。未知交接后，原 Submit 的本地传输失败只补非终结诊断；后台错误回执仍按其真实来源处理，不纳入此分支。

普通退出或 Drop 不新增 Cancel，也不声称已发请求未执行。已有取消意图时，`detach` 使用同一控制状态和补发额度有限交接，返回最后已知事实；Taken 后无需等待视图推送或 Turn 关闭。等待超时保持未知，不承诺后台完成或阻塞配置工作在该窗口内结束。

取消的具体 `LocalError` 由 LocalTurn 保存在原目标、当前用户意图的 `DetachReport.cancel_error` 中，与 Cancel 更新使用同一来源，不依赖前端消费队列。同意图补发等待、窗口到期或 Moot 保留最近已知错误；新的明确用户意图以及 true/false 成功回执清除旧诊断，旧代在途回执不写入新意图。该字段不是永久错误日志，也不改变 Taken、未接管或未知的语义。前端交接旧句柄时按报告分别显示原提交/取消身份及诊断，不把它们作为新句柄的状态或回执。

### 取消的效果与持久边界

取消控制本身在内存中，true 确认的是当前操作接管，不保证迟到取消改写已决定的结果。协调层在每次开始新模型请求或新调用前检查取消标志与本轮 deadline；槽位提交 `Started` 之后，协调层将同一取消标志与本轮 deadline 传给 `TurnTools::execute`，调用期内的取消与超时中断由工具执行器执行（执行器返回 `ToolOutcome::Cancelled` 时写入 `Terminal` 并以 `Stop { cause: Cancelled }` 关闭 Step；返回 `ToolOutcome::Deadline` 时不补写 `Terminal`，槽位留在 `Started`、读出 `Indeterminate(NoResult)`，直接以 `Stop { cause: Deadline }` 关闭 Step）。执行核心随后提交的尝试、槽位与 Step 的阶段才是进程退出后仍能读到的事实。以取消为主因关闭的 Step 以 `Stop { cause: Cancelled }` 结束，Turn 结局为 Cancelled；已写入的节点、调用结果和已发生的效果保留，取消不回滚文件。

取消或失败后，Session 当前位置停在该 Turn 最后写入的节点，已完成的步骤进入之后的上下文。用户取消通常是为了换种说法继续，已完成的工具结果仍有用；需要丢弃时，退回到该用户消息之前的节点再发送。

## 执行者消失后的 Turn

后台进程退出、执行任务异常结束或会话库写入失败之后，一个 Turn 可能停在未关闭的 Step 上。这时不需要任何补写。

- **树上已有的内容就是结局。** 这个 Step、它的尝试和槽位各自停在某个阶段，阶段给出结论，Turn 的结局按[关闭 Step 与 Turn](steps.md#关闭-step-与-turn)从中得出。已保存的结果和已发生的效果保留；只留在进程内、尚未写入的结果无法找回。
- **由后台判断它是否已经停下。** 会话库只由持有实例锁的后台进程打开，见[存储后台边界](../storage.md#本地后台与访问边界)；执行一个 Turn 需要后台内存中的 Owner 和该 Session 的执行锁。后台没有这个 Turn 的 Owner 时，没有人在执行它；视图的会话头直接说明当前位置所属那一轮有没有 Owner。后台重启后，此前未关闭的 Turn 都已停下。
- **后台不替它继续。** 后台不为停下的 Turn 请求 provider、执行 Tool 或恢复重试，也不需要当时的 profile 或 provider 凭据。
- **用户直接做下一件事。** 提交新请求或 `rewind` 不需要先处理旧 Turn。新的 UserMessage 接在当前位置之后；旧 Step 从此脱离末端位置，不能再改写。同一 Session 正在由 Owner 执行时，新写操作仍在后台准入阶段返回 Busy。

| 停下时 Step 的 `progress` | 树上已有的内容 | Turn 结局 |
| --- | --- | --- |
| `Reserved` | 没有尝试；Step 的结论为 `Stop { ProcessExit }` | Failed |
| `Requesting`，最后一次尝试 `Sent` | 该尝试的结论为 `Stopped { ProcessExit }`；Step 的结论为 `Stop { ProcessExit }` | Failed |
| `Requesting`，最后一次尝试 `Ended`（重试等待中） | 该尝试带实际原因；Step 的结论为 `Stop { ProcessExit }`，不恢复重试 | Failed |
| `Executing` | `Terminal` 的槽位带实际结果，`Started` 的为 `Indeterminate(NoResult)`，`Registered` 的为 NotExecuted；Step 的结论按[执行中 Step 的停止原因](steps.md#执行中-step-的停止原因)得出，外部停止为 ProcessExit | Cancelled 或 Failed |

停在 `Executing` 的 Step，槽位自身决定的停止（执行器返回的取消或效果不确定）优先，其余情况得到 ProcessExit。协调层已经决定、尚未提交的取消或 Deadline 不在库中，这一步按 ProcessExit 结束；已提交的关闭保持它写入的原因。

## 停止后台

`SIGTERM`、`SIGINT` 与 IPC `stop` 共用同一个停机顺序，信号处理在绑定 `api.sock` 之前就绪（就绪前收到的信号以及绑定后 listener `accept` 失败也进入同一流程）：

| 阶段 | 动作与期限 | 到期或完成结果 |
| --- | --- | --- |
| 1. 关闭准入 | 首次进入停机时记下 `deadline = 当前时刻 + drain_timeout`，停止元数据调度，调用共享认证对象的 `stop_logins()` 拒绝新登录并取消活动登录；重复请求复用同一期限与结果 | 新工作准入返回 `Stopping`；`access_token()` 保持可用，已接管的 SIWC Turn 仍可取得和刷新 token |
| 2. 排空 | 继续接受连接以服务查询、取消与 `status`（listener 出错进入停机时跳过新连接接入），等待已接管的操作（Turn、`configure`、`rewind` 及异常任务监督）与进行中的草稿会话清理收尾，无须观察者读完流；停机路径上所有等待在途工作的地方共用 `deadline` | 判定时在途工作已归零即排空完成，这一判定先于期限与信号；到达 `deadline` 或排空期间收到 `SIGTERM`、`SIGINT`（不论停机由信号还是 IPC `stop` 发起）均按排空超时处理：计入 `unconfirmed_operations` 并停写会话库。本阶段结束时保存 `DaemonStatus` 并唤醒全部 IPC `stop` 等待方 |
| 3. 元数据与认证收尾 | 继续接受连接，`status` 正常回答，IPC `stop` 取保存的结果，新工作准入返回 `Stopping`（listener 已出错时跳过新连接接入）；并发等待元数据调度任务结束、`metadata.drain()` 与认证 `shutdown()`（关闭认证 worker 与必要文件写入），共用 5 秒上限 | 到期即结束本阶段等待 |
| 4. 连接收尾 | 关闭推送并释放 listener 停止接受连接，等待连接任务结束，上限 5 秒 | 到期对剩余连接任务调用 `abort_all()` 并结束等待 |
| 5. 撤下 socket 与关闭 runtime | 三者共用一个 5 秒期限：在阻塞线程上释放最后的后台资源（排空完成时其中有会话库的最后一个引用，释放即关闭会话库），同时删除 `api.sock`；到期不再等待，用剩余的时间以 `shutdown_timeout` 关闭 runtime | `api.sock` 到期仍未删除时记为运行错误；未完成的后台任务随 runtime 关闭丢弃，不取消在途 Turn，也不伪造持久结局；到期没关完的会话库随进程退出，下次按 redb 的崩溃恢复打开 |
| 6. 进程退出与锁释放 | 持有实例锁 `InstanceLock` 直至调用进程退出，由内核在关闭文件描述符时释放 `owner.lock` | `api.sock` 先于锁撤下；锁可取得时旧后台所有用户态线程均已结束。实例锁与 socket 清理由[存储后台边界](../storage.md#本地后台与访问边界)维护 |

- **排空上限**：`daemon serve` 接受 `--drain-timeout <时长>`（非负整数加单位 `ms`、`s` 或 `m`，省略单位按秒，默认 `60s`，无效值以 `2` 退出）。
- **排空超时的停写与计数**：排空超时时，后台在准入锁内将每个尚未退休的操作计入一次 `unconfirmed_operations`（一轮草稿会话清理无论正在处理哪个候选会话都按一个操作计；已被计入的操作随后因错误退休时保持计数不变），释放准入锁后置位会话库租约的 `shutdown` 标志与 `SessionStore` 的写闸 `write_disabled`，并将会话库管理器置入终态。写闸占用每次写入从开始到提交持有的健康锁，停写只等待正在进行的那次提交结束，停写之后的会话库随最终释放关闭；此后任何写入都返回 `WriteDisabled`，在途 Turn 停在已写入的进度，见[执行者消失后的 Turn](#执行者消失后的-turn)。`unconfirmed_operations` 统计本进程未确认收尾的操作数，不等同于会话库中未关闭 Turn 的数量；连接中断也不能证明后台已停止。
- **IPC `stop` 回执与客户端等待**：IPC `stop` 在第 2 步结束时立即收到保存的 `DaemonStatus` 回执（早于元数据、认证与连接尾段），排空结束后、进入连接收尾前到达的 `stop` 直接读取同一份保存的结果。客户端收到回执后在 30 秒内等待 `api.sock` 撤下与 `owner.lock` 可取得，随后返回，调用方即可在同一状态根启动新后台（客户端不等待旧进程完全退出）；30 秒内锁仍被持有时返回 `Stopping`，由用户以 `lattice daemon status` 复核。`unconfirmed_operations` 非零时，`lattice daemon stop` 在标准错误提示有操作未确认收尾并以 `1` 退出。
- **`daemon serve` 退出码**：排空超时（含排空中收到停机信号）退出 `4`，优先于其他运行错误；排空完成但存在绑定后运行错误（如 listener 失败）或启动运行错误退出 `1`；参数错误退出 `2`；排空完成且无运行错误（含就绪前收到停机信号）退出 `0`。尾段到期不改变排空结果。
