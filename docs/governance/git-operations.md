# Git 操作与协作记录

> 类型：治理合同
> 上位依据：[Agent 身份与权限](agent-permissions.md)

## 目的与范围

本文件规定 Agent 的 Git 操作授权、提交记录格式，以及 GitHub PR 和 Agent 评论的格式。
独立身份、贡献归因、禁止强推、仓库保护及人类保留操作由上位文档规定，本文不另立例外。
文档批准与修订遵循[文档生命周期](document-lifecycle.md)。

本文件的格式要求不授予任何写权限，也不表示提交检查、GitHub 模板或权限隔离已经配置。

## 默认只读

未取得相应写操作授权时，Agent 只允许执行只读的 Git 操作。已有凭据、可写工作区、完成实现或验证通过，都不构成 Git 写授权。
GitHub 操作同样区分读取与写入；读取权限不包含创建 PR、发表评论或修改状态。

- 人类授权编辑工作文件，不自动授权修改 Git 索引、引用、历史、配置或远程状态。
  可以准备获授权的代码、文档和待发布文本，但未经授权不得暂存、提交或发布它们。
- 授权应明确操作类型、目标仓库或分支及变更范围。可以一次授权完整流程，不要求每条命令重复申请。
  “提交本次修改”不包含推送；“推送指定分支”不包含创建 PR、评论、合并或发布。
- 任务结束、授权撤回或范围改变后，不把旧任务的写权限延续到新任务。范围不清时，先询问，只继续范围明确的只读操作。
- 按实际效果判断读写，不按工具名判断。通过 Git CLI、`gh`、API、库或直接修改 `.git/` 完成的同效写入，遵守相同授权边界。

### 操作分类

| 操作 | 默认边界 |
| --- | --- |
| 查看状态、历史、对象、差异、引用或配置 | 允许在已有数据访问范围内只读查询，不修改仓库状态 |
| 查询远端引用、PR、评论和检查结果 | 仅在已有网络与数据访问范围内读取，并使用符合身份规范的认证方式 |
| 暂存、取消暂存、提交、创建或删除分支与标签、切换分支、恢复文件、stash、历史整理 | 属于本地写操作，必须获得对应授权 |
| `fetch`、`pull`、`clone` | 会写入本地对象、引用或工作文件，不属于默认只读操作 |
| 修改配置、remote、worktree、submodule，执行清理或仓库维护 | 按实际变更范围取得授权，不作为诊断或收尾的默认动作 |
| 推送、删除远程引用，创建或编辑 PR、评论、标签及任务状态 | 属于远程写操作，必须获得对应授权 |

表中写操作需要授权，不表示获得普通写授权后即可强推、越过仓库保护、合并或发布。
这些禁止与保留边界仍依[Agent 身份与权限](agent-permissions.md#操作分工)执行。

### 只读检查的副作用

只读查询也可能触发索引刷新、外部程序或网络访问，不能仅凭命令名称认定无副作用。

- `git status` 默认可能刷新索引缓存；只读检查使用 `--no-optional-locks` 禁止这类可选写操作。
- 使用已核验的内建命令与参数，避免未经确认的 alias、分页器、外部 diff 和 textconv 程序。
- 配置、过滤器、文件系统监视程序或缺失对象获取机制仍可能影响执行行为。无法确认副作用时暂停相关调用，不通过改配置或自动下载对象完成所谓只读检查。
- `--dry-run`、`--no-optional-locks` 等选项不是权限沙箱，也不保证任意命令只读。不得用它们包装写操作来绕过授权。

在已核验的执行环境中，常用本地检查形式如下：

```sh
git --no-optional-locks --no-pager status --short
git --no-optional-locks --no-pager diff --no-ext-diff --no-textconv
git --no-optional-locks --no-pager diff --no-ext-diff --no-textconv --cached
git --no-optional-locks --no-pager log -5 --oneline
```

## 获授权后的执行

1. 确认授权覆盖本次操作，核对工作区、当前分支、目标远程和身份。发现他人已有修改或暂存内容时，明确区分，不覆盖、隐藏或混入自己的提交。
2. 检查本任务的 diff 与必要验证结果。暂存时限定已核对的路径或变更块，不为清空工作区而批量纳入无关修改。
3. 提交前检查暂存区，确认其中仅有本次获准提交的变更，并核对提交消息与真实归因。
4. 推送或创建 PR 前，分别确认对应授权、目标分支与待发布提交范围，不能把无关历史一起带入。发表或编辑评论前，核对目标记录与待发布正文。
5. 操作失败、超时或结果不明时，先用只读查询确认是否已经生效，再决定重试；不盲目重复提交、推送、创建 PR 或发表评论。
6. 报告实际产生的提交、PR 或评论标识，以及未执行操作和剩余问题，不把本地成功等同于远程成功或人类验收。

可能覆盖或丢弃工作、改写本地历史、删除引用的操作，须明确说明对象与影响后取得授权。
不得把 `reset`、`restore`、`clean`、stash 或历史整理作为处理脏工作区、检查失败或推送被拒绝的默认补救。

## Commit 格式

提交标题采用 Conventional Commits 结构，摘要与正文使用中文。技术标识、命令和必要原文保持原样。

```text
<type>[(<scope>)][!]: <中文摘要>

<可选正文：原因、影响与必要说明>

<可选尾注>
```

方括号表示可选部分，不写入实际标题。`scope` 和 `!` 均可省略；标题必须单行，冒号后留一个空格。

### 标题与正文

- `type` 使用小写英文，准确描述本次变更，不用 `chore` 隐藏功能、安全或兼容性变化。
- `scope` 使用稳定的英文组件或领域名称；没有合适范围时省略，不为每次任务新造分类。
- 摘要说明实际完成的变化，不写“更新代码”“一些修复”等无法辨认目的的标题，也不把计划或验收结论写成已完成事实。
- 一个提交应构成小而完整的变更。需要正文时，标题后空一行，说明原因、重要影响和取舍；不复制整份 PR 报告或工具日志。

常用类型如下，不要求为未涉及的类别建立额外流程：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | 修复缺陷 |
| `docs` | 文档修改 |
| `refactor` | 不以新增功能或修复缺陷为目的的代码重构 |
| `perf` | 性能改进 |
| `test` | 测试修改 |
| `build` | 构建系统或依赖调整 |
| `ci` | CI 配置与流程 |
| `style` | 不改变行为的代码格式调整 |
| `chore` | 不属于上述类别的维护工作 |
| `revert` | 撤销已有变更，正文说明被撤销提交与原因 |

### 破坏性变化与尾注

- 已获授权的破坏性变化使用标题中的 `!` 或 `BREAKING CHANGE: <中文影响与迁移说明>` 尾注标明，也可以同时使用。
  仅使用 `!` 时，仍须在正文说明影响与迁移要求；标记本身不能代替破坏性变更授权。
- 尾注与前文空一行。需要关联任务时可使用 `Refs: #<实际编号>`；没有对应票据时省略，不为填字段创建 Issue。
- `Co-authored-by` 仅在存在应记录的真实共同贡献者时添加，具体身份与归因遵循上位文档，不填虚构姓名或邮箱。
- 默认使用普通关联引用。会触发自动关闭任务的关键字，仅在关闭关系与范围已获授权时使用，不能把提交或 PR 当成人类验收。

标题示例只展示格式，不表示相关变更已发生或获批准：

```text
docs(governance): 明确 Git 写操作的授权边界
fix(store): 拒绝损坏的状态引用
```

## PR 格式

### 标题

PR 标题与 commit 标题采用相同格式，概括整个 PR 的实际范围，不机械复制最后一个提交。
草案状态使用 PR 的 Draft 状态表达，不在标题堆叠 `WIP`、进度、测试数量或 Agent 身份。

### 正文

PR 正文使用以下结构。尖括号内容是填写说明，发布前必须替换；不填无信息的模板套话。

```markdown
## 目的与授权

<解决什么问题，任务或授权来源，范围与必要的非目标>

## 变更

<实际变更及关键影响>

## 验证

<实际执行的命令或人工检查、结果与证据>
<未执行或失败的验证及原因>

## 风险与待裁决

<兼容性、数据、安全或治理影响，以及需要人类决定的事项>
```

- 目的与授权注明可核验来源。可以引用 Issue、评论或明确的人类指令；对话授权没有公开链接时如实说明，不编造链接、批准身份或范围。
- 变更范围与 base/head 分支相符。规范变更、迁移、破坏性变化或权限调整须显式指出，不能藏在普通实现的描述中。
- 验证区分通过、失败、未执行与不适用。给出实际命令或检查方式；没有运行产品测试时写明原因，不用“全部通过”概括未检查部分。
- 没有额外风险或裁决事项时明确写明；仍有失败、未验证范围或阻塞时不得写“无”。
- 更新正文时保留必要的授权与审查上下文。验证结果应注明适用提交或变更范围，旧结果失效时不能继续表示为当前结果。
- 关联任务及自动关闭关系遵循本文的尾注规则。创建 PR、调整 Draft 状态或更新正文，都不能代替人类批准和验收。

## Agent 评论格式

本节适用于 Agent 发布在 Issue、PR 和审查线程中的评论。发表或编辑评论属于远程写操作，必须已有对应授权。

每条评论以固定身份头开始，正文按实际需要展开：

```markdown
> Agent：<已确认身份> | 类型：<进展 / 审查 / 验证 / 待裁决>

<具体结论与依据>

<涉及验证时给出命令、结果与证据；涉及裁决时明确请求>
```

- 身份填写实际执行者，类型选择与本条用途对应的一项，不把选项列表原样发布。需要模型信息时，只补充可核验的信息，不猜测模型或服务商。
- 简短回复也保留身份头，正文直接说明结论；不强制填满报告模板，也不发送没有新增信息的状态评论。
- 进展评论说明已完成部分、阻塞和下一步；审查评论定位文件、行或提交，说明问题、影响及依据，不冒充人类批准。
- 验证评论注明检查对象、实际命令或检查方式、结果和未验证范围。区分本地检查、远程 CI 和人工核验，不复制无关完整日志。
- 待裁决评论明确问题、可选方案和所需授权；建议不写成已经获得批准的决定。
- 更正已经发布的实质结论时，明确指出原结论、更正原因和新的依据。不得静默把失败改成通过、扩大既有授权或删除不利证据。
- PR 的正式审查批准、合并与发布仍依上位权限合同处理，评论格式不授予这些能力。

## 验证与出处

本文件只规定操作与记录格式，不要求立即增加 commit hook、PR 模板或 CI 校验器；接入自动化须另有对应授权。

文档变更检查引用、示例、格式与 diff。将来接入机器检查时，只检查可确定的结构与字段，不能用格式合规证明授权真实、证据可靠或变更已经验收。
不得为验证本文而在真实仓库创建提交、PR 或评论；实际行为验证必须另在获授权的范围内进行。

技术格式与命令行为参考：

- [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)：提交结构与破坏性变化标记。
- [Git status](https://git-scm.com/docs/git-status)：后台索引刷新与可选锁。
- [Git diff](https://git-scm.com/docs/git-diff)：外部 diff 与 textconv 选项。

外部资料解释技术行为，不产生项目授权，也不覆盖项目治理合同。
