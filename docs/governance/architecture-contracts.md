# 架构合同写作

> 类型：治理合同
> 上位依据：[文档生命周期](document-lifecycle.md)

## 目的与范围

本文件补充架构合同的内容组织、语义表达和审查要求，适用于 `docs/architecture/` 中的合同及既有文档中待迁入的架构约束。
语言、命名、文档状态、批准与迁移遵循上位规范。

架构合同应说明领域模型、关键结构、职责与接口、数据和控制如何流转，以及实现必须保持的性质。

## 边界与组织

- 按领域职责和需要共同维持的性质划分合同，使紧密关联的结构与行为能在同一上下文中理解。
- 说明适用对象、负责的职责、不负责的内容、维护归属及与相邻领域的交界。跨领域概念引用其主定义。
- 真正共享的规则明确唯一维护出处，其他合同引用它并说明本领域如何遵循。局部接口或操作的保证，不能未经说明提升为整个系统的保证。
- 采用上位规范规定的一般文档结构，正文按本领域需要组织，可以合并、调整顺序或省略不适用的部分。

## 需要表达的设计

### 领域模型与关键结构

- 说明重要实体、数据、状态及其关系，明确身份、生命周期、所有权和允许的修改者。
- 明确权威事实的来源，以及视图、缓存、索引和证据各自的作用与可信依据。依赖派生数据作决定时，说明它与权威事实的对应关系，以及失效或无法核验时的处理边界。
- 表达关键数据结构与关系约束，区分必须保持的设计与帮助理解当前实现的示意。

### 职责划分与接口

- 说明参与协作的组件分别负责什么，谁拥有状态，谁作决定，谁执行效果，以及调用方不应承担的内部责任。
- 接口说明包含输入输出的语义、调用条件和可观察效果。涉及状态、资源或跨组件协调时，还应说明所有权转移、持有期限及协作责任。
- 参数、结果、错误和事件已有明确的契约维护出处时，引用相应 schema 或协议定义并解释必要语义，不另建独立维护的字段表。说明生成产物与来源的关系；代码位置或生成行为本身不赋予规范效力。
- 区分必须保持的接口约定与可自由调整的实现细节。

### 数据流、控制流与生命周期

- 数据流说明来源、必要的验证与转换、流向及持有者；控制流说明由谁触发、判断、调度或终止操作。分别标明数据传递、调用和授权关系。
- 描述正常路径和影响架构语义的分支。有状态协议应能辨认合法状态迁移及其触发条件。
- 明确必要的先后关系、允许的并发及协调方式。区分涉及的生成、发布、持久化和完成节点，说明各自的确认条件。
- 中断、取消、重启或恢复会改变正常流转时，说明从哪些事实继续，以及哪些步骤不能再次执行。具体保证按所属操作定义。

### 行为保证与运行限制

- 将正确性、安全、并发、一致性、持久性及资源方面的要求落实到具体对象、接口或操作，说明适用条件、观察范围与边界。跨越阶段、组件或领域边界时，重新限定或引用对应定义。
- 前提、成功保证、关键失败场景、恢复责任和非保证应与上述模型、接口及流转相互对应；共享规则写一次，局部差异在对应位置说明。
- 性能目标、资源上限或重试预算属于明确承诺时，说明度量对象、单位、适用范围和核验条件。不把一次测量值或临时测试环境写成永久架构要求。

#### 前提、不变量与非保证

- 调用前提说明开始操作前必须满足什么、由谁提供和核验；不满足前提可以是正常拒绝，不自动等于实现错误。
- 不变量说明在何种范围和状态下必须持续成立；成功后的保证说明完成相应操作意味着哪些事实成立。不要把仅在终态成立的关系写成所有中间状态都成立。
- 环境假设说明保证依赖什么；非保证说明实现没有作出什么承诺。它们不能作为事后否定失败证据或削弱既有要求的借口。
- 分别说明前提拒绝、不变量破坏、环境不满足和结果未知等情形的处理责任。

#### 原子性、一致性与持久性

- “原子”应说明不可分割的是哪个对象或哪组变化，对哪些观察者、在什么条件下成立。单个路径、多个对象、一个存储库和多个存储库不能默认使用同一个原子范围。
- 分别说明原子可见性、多对象事务、并发隔离、一致性与持久性。承诺其中一种性质，不自动承诺其余性质；“一致”应落实为哪些事实之间必须维持什么关系。
- 涉及持久性时，说明确认成立的节点、所覆盖的故障范围及依赖条件。成功返回、进程重启后可见与掉电后仍可恢复，不得未经依据视为等价。
- 例如，目标路径的安装不会暴露半写入文件，并不能推出多文件一起改变、文件与历史记录一起提交，或外部进程不能同时修改文件。

#### 成功、失败与恢复

- 成功和失败必须绑定操作层级与阶段。下层一步成功不代表上层操作完成；某次变更未发生，也不代表承载它的调用没有执行。
- 区分拒绝执行、执行中失败、部分效果已发生以及结果无法确认等实际存在的情形。不能把超时或取消直接解释为未发生效果，也不为统一文案强制所有领域使用同一套错误分类。
- 对影响调用方或后续状态的关键失败，说明触发条件、已生效的变化、仍成立的事实、可观察结果，以及后续由谁处理。
- 恢复或重试说明责任主体、所依据的事实、安全前提和必要的停止条件；涉及重复执行时，说明如何避免或识别重复效果。
- 等义迁移或文字整理不得改变保证成立的条件和范围。例如，冲突检查拒绝时不改变状态，不代表执行途中的所有 I/O 失败都能保持原状态；文件安装成功而后续历史记录失败，也不能只用“操作失败”抹去已安装这一事实。

## 术语、图示与资料的关系

### 术语表与合同

- 术语表提供领域概念的简短解释、关键区别、易混淆称呼和合同入口；合同维护精确语义与完整约束。
- 多个合同复用同一领域概念时，明确主定义出处；其他合同说明本领域的责任与关系，不另立相互冲突的定义。不同概念需要共用名称时，应写明领域或使用限定名称。
- 主定义尚未完成迁移时，按上位规范保留明确的旧入口。
- 概念含义或关键区别改变时，同步核对术语表与相关合同。

### 图示与示例

- 按实际需要使用 Mermaid 结构图、数据流图、时序图或状态图。图示注明节点、连线和边界的含义，区分实体、组件、状态和部署单元。
- 区分规范性的关系与仅供理解的示意。图中的顺序、并发、状态和接口应与正文一致，省略内容不能暗示不存在的保证。
- 同一关系不在多份图表中独立维护。必要的不同视图应能对应到同一约定；图由其他来源生成时，明确维护源，不手工修改产物形成平行设计。
- 示例说明适用范围内的语义及简化之处，关键边界由正文明确。

### 实现说明与决策记录

- 区分规范要求、已核验的实现事实和待裁决的设计建议。已有约束不证明相关能力已实现，当前代码行为也不能自动成为规范。
- 实现结构、生成机制或运维命令有助于理解合同时可以引用，但应与必须保持的设计约定分开。操作细节放在相应开发或参考资料中，不复制成第二套维护内容。
- 合同保留理解当前设计所需的关键理由；完整决策过程、旧方案与历史证据由 ADR 等既有记录承载。
- 文档与事实存在冲突时，依[项目宪章](charter.md#权威传递)交由有权人类裁决，不通过选择性抄写旧文档或迎合当前代码消除冲突。

## 验证与演化

架构合同应给出关键承诺的核验方式或验证入口，使审查者能核对职责、接口、数据关系、状态迁移及必要边界。
当前执行结果和未验证范围按上位规范保留在对应任务记录中。

修订时，按实际影响检查：

- 模型、结构、接口、图示与正常及异常流转是否一致，保证是否被错误地跨阶段或跨领域传递。
- 关键条款是否能辨认适用对象、条件、效果与责任，示意或环境假设是否被误读为承诺。
- 接口或数据关系变化对调用方、已有数据和恢复路径有什么影响；明确的兼容或演化承诺如何保持或获授权修订，不为假设中的兼容预建机制。
- 术语、领域合同和既有资料是否保持唯一规则出处，未承接的有效约束是否仍有明确入口。
- 路径或锚点变化影响哪些实际读者和写入流程。文档被 skills 或工作流消费时，分别核对读取与回写入口；链接存在或旧文件改成导航，不等于消费流程兼容。

迁移的批准、替代关系和规则承接依[文档生命周期](document-lifecycle.md#迁移与唯一有效入口)执行。
