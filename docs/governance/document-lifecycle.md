# 文档生命周期

> 类型：治理合同
> 上位依据：[项目宪章](charter.md)

## 目的与范围

本文件规定项目文档的分类、归属、语言与命名、状态流转、修订和迁移方式。
权威来源、批准权限和 Agent 地位由项目宪章规定；具体架构、工程规则及实际权限配置不在本文件定义。

## 分类与归属

快慢描述文档的生命周期，不直接决定权威。慢文档中的参考资料不因此成为规范；
快文档中的已授权任务可以约束当前工作，但不能推翻上位合同。

| 类别 | 保存位置 | 职责与权威 |
| --- | --- | --- |
| 慢文档：治理、架构、工程合同 | `docs/governance/`、<br>`docs/architecture/`、<br>`docs/contract/` | 承载经人类批准的现行规范 |
| 慢文档：参考资料 | `docs/reference/` | 解释术语、接口和用法，不另立架构规则 |
| 决策记录 | `docs/adr/` | 保存决策理由、取舍与状态，不与当前合同竞争权威 |
| 快文档：任务、提案、审查 | GitHub Issue、PR 和评论 | 承载授权范围、验收标准、工作状态和建议 |
| 历史与运行证据 | Git 历史、必要归档和 CI 产物 | 用于追溯与核验，不构成当前规范 |

这些位置是目标分类，按实际需要建立，不预先创建空文档；现有材料按本文的迁移要求承接。

- 仓库保存需要长期维护的知识与规范，GitHub 保存正在推进的工作，Git 历史与产物保存过去发生的事实。
- 当前合同回答“现在应当遵守什么”，ADR 回答“为什么作出这个决定”。不得要求 Agent 翻阅整套 ADR 自行推导现行规范。
- 不另建或继续追加 `FINDINGS.md`、`FIX.md` 等任务账本，与 GitHub 重复维护状态。既有材料不得未经承接直接删除。

## 语言、命名与写作

### 语言与路径

- 项目维护的文档标题、正文、规范说明、API 文档说明、Issue/PR 模板和正式工作报告使用中文。
- 命令、代码标识符、路径、协议字段、外部正式名称、原始错误、许可证及必要的第三方原文保持原样。
- 普通文件和目录使用稳定的小写英文与连字符；`README.md`、`AGENTS.md`、`CLAUDE.md` 等约定名称保持不变。
- 慢文档以主题命名，不以当前日期、Issue 编号或实施批次命名。ADR 可以保留编号；`docs/adr/`、`docs/archive/` 不因语言要求改名。
- 最终仍在维护范围内的文档应完成中文化，不为翻译旧版本而重写 Git 历史。

### 内容与入口

- 一般文档采用“目的与范围—正文—验证或出处”的结构，不适用的部分省略。
  规范文档说明类型、状态、适用范围、约束与非目标、规则归属、上位依据及验证方式。
- 直接写事实、规则、操作和必要理由，去除套话、重复总结、空章节和模板填充。
  不把计划写成现状，不把建议写成已批准规则。
- 合同不记录当前 Issue 进度、某次测试通过数量、临时性能活动或审查流水，
  也不把“某个 Issue 完成前不得……”等阶段性状态写成永久规则。这些内容留在快文档中。
- 规则编号只用于确有跨文档引用需求的不变量，不要求逐条编号。
  文档头保持简短；批准身份与版本通过可核验记录确认，不另建重复维护的审批数据库。
- 根 `AGENTS.md` 只承担权威说明、阅读顺序、通用工作边界、冲突处理和交付要求；
  `CLAUDE.md` 只指向根 `AGENTS.md`，文档索引负责导航，不复制合同。
- 局部 `AGENTS.md` 按职责、禁止越界、必读上位文档和验证组织。
  具体键位、配色、布局、协议流程和状态机等归入领域合同，不堆入 Agent 入口。
  入口以内容聚焦为准，不为满足机械行数限制拆出碎片文档。

## 慢文档的生命周期

规范性慢文档按以下状态流转；参考资料不因长期维护而取得规范地位：

```text
草案 → 待裁决 → 现行 → 已取代 / 已废止
```

- **草案**：由人类或受授权 Agent 起草，尚不作为现行规则执行。
- **待裁决**：提交人类决定是否接受；存在未决事项时继续修订，不以等待时间或无人反对推定批准。
- **现行**：由具有相应权限的人类真实批准，并按约定生效的版本。
- **已取代**：经批准由新规范承接，明确替代文件及适用范围。
- **已废止**：经批准不再适用，不再作为当前约束引用。

### 批准与修订

- 规范的生效、修订、取代和废止依项目宪章规定取得人类批准。
  文件自填“现行”或“批准者：某人”不产生权威，提交草案不等于生效。
- 现行文件的修订在工作分支或 PR 中进行。修订获批并按约定生效前，原有效版本继续适用，除非人类明确作出其他裁决。
- 批准须能对应到具体范围与版本，以真实授权、审批及约定的合并记录核验；不得虚构批准记录，也不把 Agent 的提交或合并状态本身视为人类批准。
- 规则变化更新唯一归属文件，同时修正引用、状态和替代关系；不保留多份独立维护的同一规则。
- 旧版本通常由 Git 历史保存，不为每次修订复制归档。只有具有长期追溯价值的材料才保留在 `docs/archive/`，并明确其非现行规范地位。

## 快文档的生命周期

任务按以下语义推进，也允许待补充、拒绝和撤销等分支：

```text
待裁决 → 已授权 → 执行中 → 待验收 → 已关闭
```

- **待裁决**：说明问题或提案、拟议范围和验收标准，等待有权人类决定。
- **已授权**：取得项目所有者或受委托人类的明确指令，在授权范围和验收标准内执行。
- **执行中**：记录必要进展、阻塞与证据；使用 Issue/PR 的任务在对应记录中维护，不另建平行账本。
- **待验收**：报告实际变更、实际验证及结果、未验证部分和剩余风险，交由有权人类验收。
- **已关闭**：记录验收、拒绝或撤销等实际结论，停止作为当前任务持续追加；后续任务可以引用原有记录。

这些状态不要求立即新增一套标签或第二个状态系统，也不要求每次小改动额外创建票据。
人类直接指令可以构成授权；Agent 自行修改的标签、正文或状态不能代替授权。
Agent 的完成报告不能代替人类验收，不得通过降低验收标准取得关闭结论。

任务结束后，经批准的规则和需要长期维护的知识进入对应慢文档；提案不能仅因任务关闭而生效。
任务过程与证据保留在原 Issue/PR、Git 历史或产物中。
关闭记录退出当前工作清单和默认阅读路径，不靠删除证据实现退出。

## 从提案到规范

快文档不能通过改名、搬入仓库或修改状态自行成为规范。规范变化遵循：

```text
任务、提案或证据
        ↓
人类裁决
        ↓
修订对应慢文档
        ↓
按约定批准并生效
        ↓
实现与下位文档遵循新规则
```

- 规范和实现可以在同一 PR 中修订，不强制拆成两轮流程；修改规范须有对应授权，架构变化须有明确的架构变更授权。
- 不得超出实现任务的授权范围附带修订规范，也不为匹配当前代码而自行修改合同或削弱检查。
- 实现、测试或审查发现冲突时，按项目宪章报告并交由人类裁决；事实与证据不得为了支持某项提案而改写。

## 迁移与唯一有效入口

- 按内容职责迁移，不机械搬家。已批准规则进入对应合同，未决方案进入提案，有效任务进入 GitHub，失效内容退出现行入口。
- 每个领域在迁移期间明确唯一有效入口。新合同尚未承接的旧规则继续由明确的旧入口承接，不能因删除、移动、精简或新建草案而无声消失。
- 在迁移 PR 中说明原有规则的位置、承接位置与范围，以及保留、取代或废止的依据，供人类审查；不另建持续追加的迁移账本。
- 新合同按约定生效时，同步更新索引、局部入口和相关引用，明确替代范围，避免新旧文档同时声称同一规则的权威。
- 一项规则只有一个维护出处；跨领域不变量只收纳真正共享的硬边界，不重复抄写领域合同。
- 导航和证据链接可以双向；上位依据与授权关系不能形成相互授权、相互覆盖的循环。
  文档位置、链接方向和更新时间不决定效力，迁移本身也不构成批准。

## 维护检查

变更按影响范围核对以下事项，纯文档修改通常不启动产品测试：

| 检查方式 | 核对事项 |
| --- | --- |
| 确定性检查 | 必要元信息、有效路径与锚点、明确声明的权威依赖是否成环、入口引用是否一致、现行依据是否误指向失效规范 |
| 内容审查 | 规则是否只有一个出处、中文表达与职责分类是否合适、迁移是否完整承接、合同是否混入任务状态、文档是否过度拆分 |
| 授权与验收核验 | 批准主体、实际授权范围、批准对应的版本、约定的生效条件，以及仍待人类裁决的事项 |

这些检查项不表示已有自动化门禁。机器检查不能证明全文语义一致、内容确实全中文、人类确实授权或设计没有过度工程化等模糊或语义问题。
交付时报告实际执行的检查、结果和未验证范围，不以“遵循了文档”代替验证，也不以检查通过代替人类验收。
