# 文档写作

本文规定文档放在哪里、按什么结构写，以及怎样修改文档。目标是让读者沿结构快速找到规则，并照着执行。

## 文档放在哪里

| 位置 | 内容 | 回答的问题 |
| --- | --- | --- |
| `AGENTS.md`（根与各 crate） | Agent 入口：阅读顺序、局部职责、验证入口 | 从哪里开始 |
| `docs/governance/` | 宪章、权限、协作与写作 | 谁决定、怎样协作 |
| `docs/architecture/` | 架构合同：概念、职责、流程与保证 | 系统现在怎样工作 |
| `docs/development/` | 工程规范与操作指南 | 怎样设计、编码、测试与验证 |
| `docs/reference/` | 术语表与设计资产 | 一个词、一个值是什么意思 |
| `docs/adr/` | 决策记录 | 为什么这样决定 |
| `docs/agents/` | Agent skill 的辅助资料 | skill 怎样接入本仓库 |
| GitHub Issue 与 PR | 任务、提案、进展与审查 | 正在做什么 |

- 合同写“现在怎样”，ADR 写“为什么这样”；现行规则以合同为准。
- 任务进展、测试通过的数量和审查过程记在 Issue 与 PR 里。
- 术语的定义写在[领域术语表](../reference/glossary.md)，合同链接过去。

## 语言、命名与状态

- 正文使用中文；命令、路径、代码标识符、协议字段、外部正式名称与原始错误保持原文。
- 文件与目录名用小写英文和连字符，按主题命名；`README.md`、`AGENTS.md`、`CLAUDE.md` 保持约定写法。
- ADR 文件名为 `NNNN-<决策主题>.md`，编号依次递增。
- 合同、指南、参考资料与 ADR 在文件顶部声明状态：

```yaml
---
status: active   # 合同、指南与参考资料：draft | active | superseded
                 # ADR：proposed | accepted | superseded | rejected
---
```

## 写法

| 要求 | 做法 |
| --- | --- |
| 结构优先 | 关系与流程用表格、列表、mermaid 图和伪代码表达；段落用于必要的解释 |
| 声明式 | 每条规则写清对象、条件、动作与结果：谁在什么条件下对什么做什么，得到什么 |
| 正向 | 写应该做什么、要达到什么目的；范围之外的事项集中在一个小节 |
| 一处定义 | 每条规则只写在一个文档里，其他文档链接过去 |
| 精确 | 术语首次出现时给出定义或链接；数字写明单位、口径与适用范围 |
| 分清性质 | 已核实的事实、计划、建议与已决定的规则分别标明 |

方向检验：一份说明需要堆叠否定句才能圈出方向时，先回头检查方向本身。

### 图与伪代码

| 要表达的内容 | 形式 |
| --- | --- |
| 组件与依赖关系 | mermaid `flowchart` |
| 交互顺序 | mermaid `sequenceDiagram` |
| 状态与迁移 | mermaid `stateDiagram-v2` |
| 判定规则 | 伪代码：输入、条件分支与输出 |

图与正文讲同一件事时，以图为主，正文补充图里放不下的条件。

## 架构合同模板

```markdown
---
status: active
---

# <领域名>

<一句话：这个领域为谁提供什么能力，得到什么结果。>

## 概念

| 概念 | 含义 | 状态持有者 | 生命周期 |
| --- | --- | --- | --- |

## 组件与职责

| 组件 | 持有的状态 | 执行的规则 | 对外接口 |
| --- | --- | --- | --- |

## 流程

<正常流程的 sequenceDiagram；随后按流程中的节点展开取消、失败、重启等分支。>

## 状态

<有状态对象的 stateDiagram-v2，以及每次迁移的触发条件。>

## 保证

| 保证 | 适用范围 | 成立条件 | 依据或验证 |
| --- | --- | --- | --- |

## 范围之外

<本领域不承担的职责，以及承担它的领域。>

## 验证

<验证入口：测试、harness 场景或检查命令。>
```

- 每个概念的状态持有者与规则执行者各只有一个，见[工程规范](../development/engineering.md#归属)。
- 一份合同长到一次读不完一个领域时，改成目录：`<领域>/README.md` 写概念与组件总览，其余文件各写一个流程或子领域。

## ADR 模板

```markdown
---
status: proposed
---

# ADR NNNN：<决策主题>

## 背景

<要解决的问题、证据与约束。>

## 决策

<决定做什么。每条决策写成可执行的规则。>

## 归属

| 概念 | 状态持有者 | 规则执行者 | 只使用结果的组件 |
| --- | --- | --- | --- |

## 否决的方案

| 方案 | 否决理由 |
| --- | --- |

## 影响

<对代码、数据、合同与其他 ADR 的影响，包括取代关系。>
```

## 修改文档

- 修改规则的 PR 经维护者合并后生效。
- 移动、拆分或合并文档时，PR 附一张去向表，列出原有每条规则的新位置，或删除及理由。
- 路径或标题改变后，同步更新指向它们的链接与锚点。
- 提交前运行 `cargo xtask docs-check`，确认链接与锚点有效；再核对术语与术语表一致，同一条规则只出现在一处。
