# PR 格式与行文规范

> 类型：治理合同
> 上位依据：[Git 操作与协作记录](git-operations.md)

## 目的与范围

本文件规定 PR 标题、正文、证据引用与更新的写法，供作者准备 PR、审查者核对交付内容。
操作授权、提交身份、任务关联与自动关闭规则，以及 Agent 评论格式，遵循上位合同。
通用中文写作与文档批准要求遵循[文档生命周期](document-lifecycle.md)。

本文承接并取代 [Git 操作与协作记录的原 PR 格式章节](git-operations.md#pr-格式)，是 PR 格式与行文要求的唯一维护出处。
本文不要求新增 GitHub 模板或自动化检查。

## 标题

PR 标题采用 [Commit 格式](git-operations.md#commit-格式)，用中文摘要概括整个 PR 的实际变化。
类型、范围与破坏性变化标记沿用该规则。

- 摘要写明变更对象和行为，以整个 PR 的实际差异为准。
- 草案使用 GitHub Draft 状态表达。标题仅保留规定的格式要素。

格式示例：

```text
fix(store): 拒绝损坏的状态引用
docs(governance): 独立维护 PR 格式与行文规范
```

## 正文结构

正文按以下五节组织。尖括号内容是填写说明，发布前替换为实际内容。
“目的与授权”使用固定字段，其余各节按实际复杂度展开。

```markdown
## 目的与授权

- 目的：<要解决的问题与预期结果>
- 任务：<对应任务及其 Issue、评论链接或对话指令>
- 授权维护者：<作出授权的维护者身份及可核验的授权记录>
- 授权对象：<获授权执行任务的 Agent 或贡献者身份>
- 授权范围：<获准执行的操作、操作对象及限制条件>

## 变更

<实际变更、关键行为与必要的取舍>

## 边界

<直接改动范围、受影响的组件或使用者，以及必要的范围排除说明>

## 验证

<适用提交或变更范围、实际命令或检查方式、结果与证据>
<失败、未执行或不适用的检查及原因>

## 风险与待裁决

<剩余风险、兼容性或迁移影响、阻塞及需要维护者决定的事项>
```

### 目的与授权

必须使用上述五个具名字段，逐项填写目的、任务、授权维护者、授权对象和授权范围。
目的说明本次工作的目标；任务定位具体委托；授权维护者记录授权方及依据；
授权对象记录接受委托的执行者；授权范围说明获准对哪些对象执行哪些操作，以及适用限制。

对话授权以维护者身份和指令内容定位来源，有公开记录时附链接。
授权信息缺失或存在歧义时，在对应字段写明待确认内容，交由维护者补充。
关联任务使用普通引用；自动关闭关系遵循上位合同的[尾注规则](git-operations.md#破坏性变化与尾注)。

### 变更

按行为变化或职责组织内容，说明改了什么、为何这样改。
文件路径用于定位实现。关键取舍写理由，局部实现细节留在代码与必要注释中。

描述须与 base/head 分支的实际差异一致。规范修订、数据迁移、破坏性变化和权限调整须显式指出，
并关联对应授权；涉及规范时注明草案、待裁决或已批准的真实状态。

### 边界

分别说明直接改动范围和影响范围。直接改动范围包括本次涉及的组件、接口、配置或文档；
影响范围包括受行为、契约或依赖变化影响的调用方、使用者、数据和运行环境。

必要的范围排除说明集中在本节，例如本次没有做什么、没有修改哪些相关组件，以及保持原状的接口或行为。
仅列出有助于界定责任或避免误解的事项。失败和未执行的检查在“验证”节记录，其交付后果在“风险与待裁决”节说明。

### 验证

验证记录应让审查者判断检查了什么、结果是什么，以及结论适用于哪个版本。

- 标明适用提交或明确的变更范围。检查针对未提交工作区时，如实说明被测内容及其与 HEAD 的关系。
- 给出实际执行的命令或人工检查方式，以及结果。需要环境条件、参数或产物才能复核时，一并提供。
- 分别记录通过、失败、未执行与不适用。产品测试的执行情况及原因须明确说明。
- 区分本地验证、远程 CI 和人工核验。结论限定在实际检查覆盖的范围内，维护者验收以对应记录为依据。
- 正文保留判断所需的结果摘要；较长日志、报告和产物使用可定位的引用。

表格只在多项检查需要对照时使用。一次检查用一句话写清命令、结果与范围即可。

### 风险与待裁决

说明剩余的兼容性、数据、安全或治理影响，必要时给出迁移要求与恢复办法。
未验证范围和失败若影响交付判断，应在此说明后果或阻塞，不重复粘贴验证记录。

需要维护者裁决时，写明具体问题、可选方案及建议；建议与已经批准的决定分开表述。
没有额外风险或裁决事项时明确写明。仍有失败、未验证范围或阻塞时，不得笼统写“无”。

## 行文要求

- 开头直接说明问题或实际变化，使用具体的对象与行为描述。
- 禁止“肯定……，否定……”的表述和逻辑，包括先陈述成果、再用否定句衬托或重复限定成果的写法。直接写明事实及其成立条件。
- 避免不必要的否定陈述。必要的“没有做什么”“没有改什么”等范围排除说明统一放在“边界”节。
- 禁止不必要的数据强调。数字仅用于解释行为、界定范围或支持验证结论；测试数量、文件数量、代码行数等不得用来渲染工作量或完成度。测量数据须保留判断所需的条件、口径与依据。
- 区分事实、推断和建议。性能、安全性或可靠性结论须与证据及其适用条件相符。
- 同一事实放在最合适的章节。其他章节只补充不同含义，例如验证记录写失败结果，风险章节写该失败对交付的影响。
- 使用稳定的领域术语。命令、路径、代码标识、原始错误和必要原文保持原样。
- 每段或列表项围绕一个要点。优先短段落与列表；需要逐项对照的信息使用表格，标题与强调格式用于帮助定位内容。
- 将讨论中的澄清落实为准确正文，保留必要的条件、边界和取舍。

## 更新与审查上下文

PR 正文维护当前交付状态。追加提交后，核对标题、范围、风险和验证记录是否仍然成立。
旧检查未覆盖新变更时注明适用版本或待重新验证，不继续将其表示为当前版本的通过证据。

更新正文须保留必要的授权与审查上下文。实质结论发生更正时，说明原结论、更正原因和新依据，
保留可追溯记录，不静默把失败改成通过或删除不利证据。
评论和审查线程的记录格式仍按上位合同执行。

## 发布前核对

发布或更新前检查标题与实际范围、正文各节、授权字段、引用目标、验证适用版本及未决事项。
核对“边界”节是否覆盖改动范围与影响范围，并检查行文禁则的遵循情况。
删除填写说明与无信息套话，确认内容符合凭据与数据披露要求。

结构、字段和链接可以辅助检查；授权真实性、证据充分性、表达准确性及批准和验收状态须结合内容与对应记录核验。
